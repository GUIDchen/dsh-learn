# 界面布局与排版调研（含本项目对照与改造清单）

> 调研目的：为 dsh-learn 的网页版与原生端找一套**有出处、可落地**的布局与排版规则，避免继续凭手感改界面。
> 结论部分可直接执行；对照部分给出本项目现状的实测数字与差距。

## 0. 一句话结论

三栏（导航 / 主任务 / 辅助结果）是这类工具型应用的通行骨架，但**第三栏属于"支持性面板"，只应在宽屏出现**；
排版上只需 **3–5 档字号**、行高与行宽/字号成反比、**不用细字重**、数字用等宽；
间距统一走 **8pt 基准（4px 细分）**；顶栏放全局上下文与动作，**关键信息与控件不要沉到窗口底部**（macOS 明确建议）。

## 1. 布局骨架：三栏的通行做法

### 1.1 三个分区各自的分工

| 分区 | 放什么 | 不该放什么 |
| --- | --- | --- |
| 左（导航/列表） | 可枚举的对象清单、筛选、分组、进度总览 | 需要横向空间的详细内容 |
| 中（主任务） | 当前对象的完整内容 + 主要操作 | 次要统计、跨对象汇总 |
| 右（辅助/结果） | 与当前选择**相关**的细节：结果、属性、历史、检查器 | 与选择无关的全局信息（那属于顶部或独立页面） |

参考：Apple HIG 的 Layout 讲的是更上层的原则——"**把相关的项目分组**"、"**给关键信息足够空间**"、
"**区分控件与内容**"、"**用位置表达相对重要性**"、"**对齐**"、"**渐进披露**"、"**控件周围留够空间并按逻辑分区**"。
三栏的职责划分就是这些原则在工具型应用里的常见落地。

### 1.2 宽度与断点：Material 3 的窗口尺寸类

Material 3 把宽度分成五档（dp/px，经 m3_layout 的实现页确认数值）：

| 档位 | 宽度 | 典型设备 | 常见骨架 |
| --- | --- | --- | --- |
| compact | < 600 | 手机竖屏 | 单栏（导航折叠进抽屉/底栏） |
| medium | 600–839 | 平板竖屏 | 两栏（列表 + 内容） |
| expanded | 840–1199 | 平板横屏 / 桌面 | 两栏或**两栏 + 支持性面板** |
| extraLarge | 1200–1599 | 桌面 | 三栏稳定成立 |
| ultraWide | ≥ 1600 | 宽屏桌面 | 三栏 + 更宽的主内容 |

搭配的三种"经典布局"：list-detail（列表-详情）、**supporting pane（主内容 + 支持面板）**、feed（信息流）。
工具型应用基本就是 list-detail 加一个 supporting pane。

值得记的两条边界：

- **支持性面板（第三栏）出现在 expanded（≥840）之后才合理**，宽度紧张时它的下限（通常 280–360）会把主内容挤瘦；
- 大屏应当"**用更少的嵌套层级、更少模态**呈现更多内容"，但密度要舒服到"不用凑近看"（HIG 对 macOS 的原话大意）。

### 1.3 什么时候降级

三栏 → 两栏 → 单栏，判据不是"窗口能不能塞下三栏的最小宽度"，而是"**主内容是否还够用**"：
主内容低于约 560–640px 时，交互（写命令、看输出、读长文）就开始难受，此时应把第三栏收成可切换的面板或挪到底部，而不是继续压。

### 1.4 窗口最小尺寸

最小窗口宽度 ≥ 各栏 minWidth 之和 + 栏间距 × (栏数-1) + 两侧内边距。**这条容易被忽略**：
只要最小尺寸贴着这个和，用户一拖窗口，最先被牺牲的就是最该看的内容（本项目原生端上一轮就踩过：题单被挤到只剩两行半）。

## 2. 模块放置位置

### 2.1 位置与语义的对应

| 位置 | 语义 | 本项目对应 |
| --- | --- | --- |
| 顶部横条 | 全局：版本、环境、身份、平台、全局动作 | 版本 / 服务端平台 / 评测平台 / 在线状态 / 快捷键提示 |
| 左栏 | 集合与筛选：我要在哪个范围里、有哪些对象 | 轨道、难度、搜索、题单、进度摘要 |
| 中间 | 当前对象的完整内容与主动作 | 题干、目标、作答输入、判定/清空/验证按钮 |
| 右栏 | 与当前对象相关的辅助信息与结果 | 判定结果、复习队列、笔记、提交历史 |
| 底部 | 状态与低频设置 | 备份导出/导入、更长的设置项 |

两条硬约束：

1. **macOS 上不要把控件或关键信息放在窗口底部**（HIG 的 macOS 条目明确写了）。底部适合状态栏与低频入口。
2. **同一屏里只放一件事**：主任务的按钮不应与全局设置混在同一视觉块里，否则用户会误以为按钮作用于全局。

### 2.2 视觉层次（HIG 的 Visual hierarchy 条目）

- 用**位置**表达重要性（重要的靠上、靠左、靠中）；
- 用**对齐**让界面可扫读（同组左对齐、数字右对齐）；
- 用**渐进披露**把暂时不需要的收起来——收起来的东西要有明确的入口与名称（本项目左栏"更多：轨道完成度 / 学习目标 / 备份"就是这个做法）。

### 2.3 为什么要这样放：F 型扫描

眼动研究显示用户对网页内容的常见扫描是 F 型：**先横着读顶部一整行，再往下读一条更短的横线，最后沿左侧竖着扫**。
推论：**左上角是视野的黄金位置**（放当前对象的名字、状态、最重要的一条信息），越靠下越容易被跳过；
同时 F 型本身是设计的症状——标题清晰、关键词前置、段落短小、适当用列表，就能把"扫"变成"读"。

## 3. 字体

### 3.1 字号阶梯：3–5 档就够

Ant Design 的字体系统给出的可引用基准：**正文 14px 配行高 22px**（约 1.57），
并且建议"在一个设计系统里（展示页除外）**字号梯度控制在 3–5 种**"。
字重也类似：**多数场合 regular(400) 与 medium(500) 足够**，需要强调的粗英文可以用 semibold(600)。

Apple HIG 从另一侧给同一条建议：**尽量减少字体种类（minimize the number of typefaces）**，
层次靠"**字重 + 字号 + 颜色**"三者一起调，而不是靠加字号档位。

### 3.2 行高：与行宽正相关，与字号反相关

Refactoring UI 的观点值得背下来：**行高与字号成反比**、与行宽成正比——
窄文本 1.5 够用，宽文本可能要到 2；小字需要更多行距，大标题 1.0–1.2 也成立。
（"统一 1.5"是起点，不是答案。）

### 3.3 可读性红线

- **避免细字重**（HIG 明确写"in general, avoid light font weights"）；
- 正文不要小于 14px（Ant 把基准从 12 提到 14 的理由是"50cm 观看距离下的最佳阅读效率"）；
- 次要信息可以到 12–13px，但**不要再小**；
- 对比度按 WCAG AA：正文 ≥4.5:1，非文本 UI ≥3:1（本项目已按此加了主题护栏）；
- 尽量少截断（HIG：keep text truncation to a minimum）；
- 支持系统字号变化（macOS/iOS 的 Dynamic Type；网页端不要写死 px 到无法放大）。

### 3.4 数字用等宽

Ant 专门提醒：需要纵向对齐的数字应设 `font-variant-numeric: tabular-nums`。
分数、计数、耗时、时间戳这类一列数字，比例数字会让列看起来"歪"。

### 3.5 中文排版注意

- 中文没有词间空格，**行高要比同字号英文更宽松**（正文 1.6–1.8 更稳）；
- 中英文混排时，标点用全角、数字与英文两侧留 1/4 空隙（或直接不强行加空格，保持系统默认）；
- 正文用系统字体即可（`-apple-system` / `PingFang SC` / `system-ui`），**不要为了"好看"引入网络字体**（离线与首屏都受影响）；
- 等宽字体只用于**命令、路径、ID、代码**，不要拿它排中文正文。

## 4. 间距与密度

### 4.1 8pt 基准 + 4px 细分

两套设计系统的口径一致：**所有布局间距走 8px 的整数倍**，密集处用 4px 细分。
一份实践建议把它讲得很具体：

- **4–16px 区间以 4px 递增**（组件内部的图标间距、输入框内边距、行内标签偏移）；
- **16px 以上以 8px 递增**（布局级间距）；
- 密度分三档：**紧凑 8px 内边距 / 4px 间隙**（徽标、标签、行内图标）、**舒适 16 / 8**（按钮、卡片、输入框、弹窗）、**宽松 32 / 16**（页面区块）；
- 常见阶梯：0 / 2 / 4 / 8 / 12 / 16 / 24 / 32 / 40 / 48。

另一套系统的阶梯是 0 / 4 / 8 / 16 / 24 / 32 / 48 / 64 —— 数值不必完全一致，**关键是同一套系统内只用一条阶梯**。

### 4.2 密度不是越小越专业

密集界面（开发者工具）常见误区是"信息越多越好"。HIG 的 macOS 建议是**用更少的嵌套层级与更少模态来放更多内容，同时保持不用凑近看的舒适密度**。
本项目的每一条取舍都应该能用一句"给谁省了什么"解释清楚。

### 4.3 点击目标

本项目已在用：**24×24 是最小可点区域**（WCAG 2.2 AA SC 2.5.8），触屏场景应更大（44×44 的经验值）。

## 5. 对照本项目现状（实测数字）

### 5.1 网页版

| 项 | 现状 | 评价 |
| --- | --- | --- |
| 字号令牌 | `--fs-xs 12`（标签/徽标/kbd）、`--fs-sm 12.5`（次要文字/pre）、`--fs-md 13`（表格/题单行/h2）、`--fs-body 14`（正文）、`--fs-lg 15`（题目标题）、`--fs-xl 18`（h1） | **6 档，且 12.5/13/14/15 挤在 3px 内**：梯度失焦，13 与 14 同屏时读者分不出层级 |
| 行高 | `1.6`（14px → 22.4px） | ✅ 与 Ant 的 14/22 一致，中文也够 |
| 数字对齐 | **没有 `tabular-nums`**（0 处） | ❌ 表格/统计里的分数、条数不会对齐 |
| 三栏宽度 | `minmax(200,272) / 1fr / minmax(0,360)`，gap 12 | ✅ 比例合理 |
| 断点 | ≤1280 三栏收窄（232/1fr/300）→ ≤1024 再收（190/1fr/240）→ ≤860 两栏（右栏通栏下移）→ ≤700 单栏 | ⚠️ **1024–860 之间仍是三栏、右栏只剩 240px**；按 M3 的边界，支持性面板到 expanded（≥1200 更稳）才出现。注意：CSS 里有注释说明"1024px 起就保持左中右三栏"是**有意为之**（不想让提交历史被挤到页面底部），所以这是一处**取舍**而非疏漏——要么接受 240px 的右栏，要么改成抽屉/下方面板 |
| 间距 | 12 / 16 / 24 | ✅ 落在 4/8 的阶梯上 |
| 主题 | 浅/深两套令牌 + 对比度护栏 | ✅ 超出通行做法的部分 |

### 5.2 原生端（SwiftUI）

| 项 | 现状 | 评价 |
| --- | --- | --- |
| 字号用法 | `.caption` **48 处**、`.callout` 13、`.subheadline` 11、`.headline` 3、`.body` **1**、`.title` 1 | ❌ **caption（11pt）占绝对多数**，与 HIG"用多数人能轻松读的字号"相悖；`.body` 只有 1 处说明没有"正文"概念 |
| 列宽 | 240（理想 310）/ ≥380 / 300（理想 350） | 合计 ≈ 950–1040 |
| 窗口 | 默认 1320×840，**最小 980×620** | ⚠️ 最小宽度 980 贴着三栏最小宽之和；最小高度 620 会让题单只剩两行（上一轮已用折叠缓解，列宽问题同样存在） |
| 数字等宽 | `.monospacedDigit()` 6 处 | ⚠️ 有但少，分数/条数仍有不对齐的地方 |
| 颜色 | 全部语义色（随系统深浅色） | ✅ 符合 HIG |

### 5.3 两条从实测里得到的教训（与调研结论一致）

1. **最小窗口尺寸要按内容需要定，不是按"能塞下"定**——980×620 让最该看的题单只剩两行。
2. **字号档位越少越清楚**——12/12.5/13/14/15 这五档在屏幕上几乎没有可辨差异，反而让"什么更重要"变得随意。
