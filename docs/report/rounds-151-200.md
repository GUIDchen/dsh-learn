## 5.151 平台矩阵收口：最后 7 道该补 Windows 的题（第 148 轮 / 共 250 轮）

### 这轮要解决的问题

第 137–138 轮把 win32 纳入体检、补了 15 个 Windows 变体，缺口一度清零。但**"缺口"是按声明算的**：
后来盘一遍清单，发现还有 12 道题没有 win32 变体，其中 5 道是**显式声明过"只在 darwin/linux 成立"**的
（`launchctl`、`pkgutil/dpkg`、bash 3.2 与 4 的三道 shell 题）——那 5 道不欠；
剩下 **7 道是真欠着**：这些事在 Windows 上照样要做，只是没人写参考答案。

### 补的 7 个 Windows 变体

| 题 | Windows 参考答案（要点） |
| --- | --- |
| ops.checksum-file | `(Get-FileHash dist\app.tar.gz -Algorithm SHA256).Hash + '  dist/app.tar.gz' \| Out-File … -Encoding ascii`（Windows 没有 sha256sum/shasum） |
| netops.ports-listening | `netstat -ano \| findstr LISTENING`（`-a` 全部、`-n` 数字端口、`-o` 带 PID） |
| netops.dns-system-resolver | `Resolve-DnsName example.com -Type A`（走系统解析器，不是 nslookup/dig） |
| netops.bandwidth-instant | `Get-NetAdapterStatistics` 采两次 + `Start-Sleep 1`，再用**两次相减**算速率 |
| netops.interface-brief | `Get-NetIPConfiguration \| Select-Object InterfaceAlias,IPv4Address,NetAdapter` |
| perf.iostat-interval | `Get-Counter '\PhysicalDisk(_Total)\Avg. Disk sec/Read' -SampleInterval 1 -MaxSamples 5` |
| perf.cpu-top-snapshot | `Get-Counter '\Process(*)\% Processor Time' -MaxSamples 1 \| … Sort-Object CookedValue -Descending`（采一次就走） |

每条都按老规矩带**禁止写法**把别的平台的习惯挡在外面：`lsof`/`ss`/`ip`/`ifconfig`/`iostat`/`top`/`vmstat`/`dig`/`nslookup`/`/sys/class/net`/`netstat -ib`/`certutil`/`MD5|SHA1`。

### 一处"看起来通过、其实没判住"的写法（自查时抓到）

写 `netops.bandwidth-instant` 第 4 条要素时我先写成了 `[-+]|减法|diff`——
`[-+]` 是**字符类**，任何单个加号或减号都算命中，等于这条要素没判任何东西。
换成真正表达"两次采样相减"的正则 `\$[A-Za-z0-9_]+\.[A-Za-z]+\s*-\s*\$`（匹配 `$b.ReceivedBytes - $a`），
并当场用 `new RegExp(rule.p).test(sample)` 验了一遍是 true。
顺带一提我第一版把正则多转义了一层（存进去的是 `\\$`），也是这条自检抓出来的——
**规则写完必须跑一次"能不能匹配上自己的参考答案"**，这条已经成了流程的一部分。

  同一条答案在 `--platform darwin` → **0 分**，缺的是 macOS 那套（`-w`/`-c`，且 BSD 的 iostat 没有 `-x`）；
  把 Linux 写法 `ip -br addr show` 丢到 win32 → **0 分**，并命中禁止项"Windows 没有 ip 命令"。

### 4. 顺手抓到的真问题：首屏会自己往下滚 475px

截图核对时发现页面标题与环境行"不见了"。用 CDP 给 `scrollIntoView` / `scrollTo` / `focus` 打点（`Page.addScriptToEvaluateOnNewDocument` 注入包装函数记录调用栈），拿到确凿结论：

```
scrollIntoView:task-item active ← renderTaskList (app.mjs:544)
scrollY = 475
```

根因：`renderTaskList()` 末尾无条件对选中项调 `scrollIntoView`。宽屏下左栏是 sticky + `overflow:auto` 的容器，而 `scrollIntoView` 会**连带把所有可滚动祖先（包括文档）一起滚**——于是首屏就把页面滚掉 475px，标题与环境行被顶出视口。

修法（三处，都在 `web/app.mjs`）：

1. 只在**显式切题**时滚动：`renderTaskList()` 不再滚，`goToTask(id, { scroll })` 负责；首屏恢复题号时传 `scroll: false`；
2. 宽屏下**只滚左栏自己的容器**（用 boundingClientRect 差值改 `scroller.scrollTop`），不碰页面；
3. 堆叠模式（左栏没有自己的滚动条）只有在那一行**确实看不见**时才回退到 `scrollIntoView`；另外把两处 `answer.focus()` 加上 `preventScroll: true`。

实测：`scrollY` **475 → 0**，标题与环境行回到视野（截图 [web-topbar-1280-0.116.0.png](docs/evidence/web-topbar-1280-0.116.0.png)）。新增守卫：`test/page.test.mjs` 断言首屏恢复传 `scroll: false`、堆叠模式只在看不见时才滚、聚焦输入框必须带 `preventScroll`。

### 5. 一个环境坑（记下来免得再犯）

中途 `verify.sh` 报了 **PASS 72 / FAIL 4**，四条全在"远程 agent"一节，报 `no route /agent/health`。

### BOSS 直聘这类站点：从"看着成功"改成"如实说没抓到"

实测 BOSS 对非浏览器请求返回的正文只有 71 字：「请稍候 - BOSS直聘　B O S S　正在加载中...」——既过了原先 40 字的下限，
也没有命中任何已知反爬词，于是被当成正常页面分析，输出"识别出 1 个知识点"。用户在界面上看到的是成功，实际抓到的是壳。

修法：`fetchText` 增加反爬识别（`detectBlockedPage`）——命中特征词**且**正文很短才算拦截，避免误伤"讲验证码的技术文档"：

```
抓取失败：页面是验证页 / JS 壳，不是正文（命中：请稍候、正在加载中、正在加载）——这类站点对非浏览器请求做了反爬；
可行路径：① 截图（本机 OCR，离线）② 把正文复制成文字粘进来 ③ 登录后带 Cookie 再试（--cookie / --cookie-file）。
```

实测三态：验证页 → 拦下（markers 命中）；71 字的 BOSS 壳 → 拦下；几千字文档里提到"验证码" → 不拦（放行）；普通命令文本 → 不拦。
顺手补齐了 `&copy;` 等 HTML 实体（BOSS 壳页里就是字面量 `&copy;`，会被当成正文喂进分析器）。

### 关键设计决定：用户题库与随工具发布的题库**分开放**

第一版把 promote 的目标定成仓库里的 `packs/`，结果在 /tmp 的仓库副本里实测：**6 条护栏全红**——
文档里的题库数字、知识点对账、判定强度基线、结构校验都以 `packs/` 为准，用户内容混进去等于把"随工具发布的题库"改了。

改成两个目录后：

### 截图核出来的两个真问题

1. **项目页一直停在空态**：索引接口 `/api/project?action=index` 里的草案 `tasks` 是**对象数组**，而原生沿用列表接口 `/api/draft` 的 `tasks: Int`（数量）→ 整包解码失败，界面只显示"左边点一个项目…"。
   修法：索引里的草案用独立的 DTO（`ProjectIndexDraft`），并在右侧空态旁**显示读取失败的原因**（只显示空态会让人以为"这个项目什么都没有"）。
2. **改状态会丢 JD 分析结果**：网页版编辑表单、CLI `update`、原生端保存都会提交一份不带 `analysis` 的表单，归一化后 `analysis = null` 把它抹掉。
   修法放在 `core/jobs.mjs` 的 `mergeJob`：入参没带 `analysis` 时保留原值——**一处修，三端都受益**，并补了一条用例钉住。

### 顺带修的编译问题

SwiftUI 对"闭包 + 三元 + 多条链式修饰"的长表达式会报 `unable to type-check this expression in reasonable time`（这轮踩了两次）。
修法是把列表行、统计行抽成独立函数 / 计算属性——和网页端"一个函数只做一件事"是同一个道理。

## 5.159 能力①：链接搜索并解析收集信息（第 156 轮 / 共 250 轮）

长期目标（本轮建 goal）是把三项能力补齐并串成闭环，这轮先补**最缺的一项：软件自己会搜**。
在此之前，工具只能"给一个链接然后抓它"，没有搜索能力。

### 多引擎 + 依次回退（为什么不是只押一个）

实测本机环境：`html.duckduckgo.com` / `lite.duckduckgo.com` **连不上**（curl 返回 000），而 `www.bing.com/search` 正常（200 / 98KB / 6 条 `b_algo`）。
只押一个引擎，用户换个网络就废了。所以：

- 默认顺序 **bing → duckduckgo**；任一成功即返回，并把"谁失败、为什么"记在 `tried` 里；
- `DSH_LEARN_SEARCH_ENDPOINT` 可指向自建/内网搜索（`engine=custom`），任何返回带链接 HTML 的端点都能用；
- 全部失败时给一句能照着做的原因（含"可以设 DSH_LEARN_SEARCH_ENDPOINT 或直接粘贴链接"）。

解析规则两套 + 一套兜底：Bing 走 `li.b_algo`（标题/链接/摘要），DuckDuckGo 走 `result__a`（并把 `uddg=` 跳转链还原成真实地址，否则存进项目的地址之后只会 404），
两套都解析不出时退回"任意 `<a href=http…>` + 锚文本"——页面结构变了也不至于空手而归。

### 三端入口

| 端 | 入口 |
| --- | --- |
| CLI | `search <关键词>`（只看结果）/ `research <关键词>`（搜 → 逐页抓 → 抽知识点与草案题）/ `--project=名字` 直接收进项目 |
| 网页版 | 学习页分析面板：「搜一下 / 搜索并解析 / 解析并收进项目」+ 结果列表 + 「练这些题」 |
| 原生端 | 项目面板里的「搜索并解析」：同一个搜索框 + 三个按钮 + 结果列表（单开 `SearchBox` 视图，避开 SwiftUI 的 type-check 上限） |

| 场景 | 结果 |
| --- | --- |
| CLI 真搜 | `search 'kubectl rollout restart'` → 引擎 bing，3 条结果（标题 + 链接 + 摘要） |
| CLI 搜索并收进项目 | `research 'kubectl rollout restart deployment' --limit=2 --project=搜索测试` → 搜到 2 / 抓到 2 → 2 个来源 6 个产物；项目索引 **57 个知识点 → 221 道可练题**，2 份草案各 20 题 |

### 顺带修的一个真问题

原生自检里 `setenv` 设了 `DSH_LEARN_SEARCH_ENDPOINT`，引擎子进程却没收到——因为 `ProcessInfo.processInfo.environment` 是**进程启动时的快照**，运行期 setenv 不会反映进去。
修法：spawn 时显式透传这几个运行期设置（`DSH_LEARN_SEARCH_ENDPOINT` / `DSH_LEARN_PACKS` / `DSH_LEARN_OCR` / `DSH_LEARN_OCR_LANGS` / `DSH_LEARN_GIT_MIRROR`），用 `getenv` 读实时环境。
这条对用户也有意义：从 shell 启动 App 时设的这些变量现在能到达引擎了。

### 已知边界

- 搜索依赖外部引擎的 HTML 结构，结构大改时靠兜底解析顶上（会少摘要，但链接还在）；
- 反爬站点（知乎 403、BOSS 验证页）搜得到链接但抓不到正文——如实报原因，并提示用截图 / 粘文字 / Cookie；
- 搜索不落盘、不建立索引；要留下来就 `--project` 或界面上的「解析并收进项目」。

### 识图解析：先能自证，再谈识别

OCR 本身早就有（macOS Vision 离线识别，其它平台 tesseract / `DSH_LEARN_OCR`），缺的是**能力矩阵**：用户无从知道这台机器到底能不能识图。
新增 `ocrCapabilities()`（CLI `ocr --capabilities`、`GET /api/ocr`、原生端界面上一行），把三个引擎的可用性、当前状态、**开启方式**（`xcode-select --install` / `brew install tesseract tesseract-lang` / `export DSH_LEARN_OCR=…`）、
支持的格式与大小上限、以及"当前会用哪个"一次说清；一个都用不了时直接给"怎么开"，不假装能识别。

实测：`node src/cli.mjs ocr --capabilities` → `平台 darwin　选用 vision`（custom/tesseract 如实报不可用 + 开启方式）；
`node src/cli.mjs ocr docs/evidence/web-topbar-1280-0.116.0.png` → **识别出 114 行**（Vision 助手在临时 home 里自动编译）。

### 文字描述理解：从"命中哪些知识点"到"这是什么、要什么、哪些是硬要求"

原来的分析只能回答"涉及哪些知识"；流程要往下走（简历、岗位推荐、项目生成）必须知道更多。`core/understand.mjs` 把自由文本读成结构：

| 字段 | 怎么来的 |
| --- | --- |
| 分类 `kind` | 有职责/要求分段或两行以上"熟悉/了解"类词 → 岗位描述；有命令块 → 技术文档；否则随手笔记 |
| 公司 / 岗位 | 第一行常是「公司 招聘 岗位」，按它拆；拆不出来再按 `公司：` / `岗位：` / 岗位词各自匹配 |
| 级别 / 年数 | 应届·初级·中级·高级·专家 + `N 年经验` |
| 硬要求 / 加分项 | 命中「熟悉·掌握·精通·要求…」→ 硬要求；命中「了解·加分·优先…」→ 加分项（同一条同时命中时按加分项算，先松后紧）；**每条都带命中的那个词作为依据** |
| 职责分段 | 按「岗位职责 / 任职要求 / 加分项 / 团队」小标题切段 |
| 技术栈 | 已知技术词表命中（与知识点互补：一个给名字，一个给知识点） |
| 知识点 / 可练题 | 复用同一份字典（三端一致） |
| `why` | 分类/公司/岗位/级别的判断来源，便于复核 |

实测（同一段 JD）：`岗位描述　某某科技 · 高级运维工程师　高级　硬要求 2 条 / 加分 1 条　技术栈 kubernetes、python、linux、shell、terraform　知识点 2 个 → 可练题 9 道`。
踩过的两个坑：① 小标题「任职要求」自带"要求"二字，会被当成一条硬要求 → 小标题不参与分档；② 第一行「某某科技 招聘 高级运维工程师」会整体被当成岗位名 → 按「招聘」拆开再 tidy 掉分隔符。

## 5.161 求职学习闭环：七步串起来（第 158 轮 / 共 250 轮）

三项能力齐了之后，这轮把它们串成**一条闭环**，并且每一步的状态都**从真实数据推出来**（练习记录 / 项目目录 / 投递记录），不靠用户自报：

```

| 模块 | 做什么 |

| `core/flow.mjs` | 七步状态机：每步给 `done / doing / todo`、进度文字、**依据**与「下一步」动作（还带 CLI 命令）；岗位匹配度 = 这道 JD 能练的题里已通过多少，差的就是补课清单 |
| `core/resume.mjs` | 按练习记录生成简历要点：技能（按通过题数排序，带困难题数）、亮点（**每条带依据**）、项目经历（来自项目目录）、待补方向、Markdown 导出 |

简历那一环的边界写在代码与文档里：它生成的是**学习成果摘要**，不是替用户编工作经历的生成器；
markdown 末尾直接印着「只陈述练习记录里的事实，不含虚构的工作经历」。

| 原生端 | 顶部第 4 段「流程」：同一份 `FlowPage`（七步 / 简历 / 粘 JD / 推荐 + 记投递） |

## 5.162 按岗位生成「项目 + 学习计划」+ 截图入库（第 159 轮 / 共 250 轮）

## 5.163 匹配度加权 + 按链接抓 JD（第 160 轮 / 共 250 轮）

上一轮留的两条边界：匹配度只看通过比例、招聘站点只能靠粘/截图。这轮各往前走一步。

### 匹配度从"通过比例"升级成"加权分 + 逐项依据"

原来的口径是「这道 JD 能练的题里已通过多少」，问题是**换个方向可能全 0，硬要求与加分项也不分轻重**。现在：

| 项 | 权重 | 口径 |
| --- | --- | --- |
| 覆盖 | 55% | 这道 JD 能练的题里已通过多少 |
| **硬要求** | 30% | JD 里「熟悉/掌握/精通」那几行**逐行过一遍知识字典**映射到知识点，再算这些知识点的题通过比例 |
| 方向广度 | 15% | JD 涉及的方向里练过的方向占比（换方向时不至于全 0） |

输出的 `why` 逐项写清：`覆盖 5/10 道（权重 55%）`、`硬要求对应的题 2/7 道（权重 30%）`、`方向覆盖 1/4（k8s、ops、database、perf）（权重 15%）`。
**老记录没存硬要求时如实降级**：`这条记录没存硬要求（老数据）：只按覆盖与方向算`（权重 85/15），不假装算过。

为了让加权有数据可用，`analyzeJd()` 现在把文字理解的结果一起存进记录：`mustHave` / `niceToHave` / `stack` / `seniority` / `company` / `position`
（原来只存知识点与可练题），投递材料与匹配度都读同一份，不再各算一遍。

### 按链接抓 JD：Cookie 用环境变量，三端共用

`flow collect` 现在四条输入路径，进的都是同一份投递记录：

| 路径 | 用法 |
| --- | --- |
| 粘正文 | `flow collect --file jd.txt` / `--text 「…」` |
| 截图识图 | `flow collect --ocr jd.png` |
| **按链接抓** | `flow collect --url <链接>`（登录站点：`export DSH_LEARN_COOKIE='…'` 或 `DSH_LEARN_COOKIE_FILE=cookies.txt`） |
| 批量搜 | `flow collect --query=「…」`（搜不到 JD 会如实说明并给替代路） |

Cookie 走环境变量而不是三端各加一个输入框：`readCookies()` 现在按「显式参数 → `DSH_LEARN_COOKIE` → `DSH_LEARN_COOKIE_FILE`」取值，
CLI / 网页版 / 原生端 / API 用同一套；原生端 spawn 引擎时也已经显式透传环境变量（前面那轮修过）。

### 实测

| 场景 | 结果 |
| --- | --- |
| 按链接抓文档页 | `flow collect --url https://kubernetes.io/zh/docs/reference/kubectl/` → 入库并如实标注「技术文档」，还提醒「确实想留就留着，不想要：jobs delete <id>」 |
| 按链接抓反爬站点 | `--url https://www.zhipin.com/job_detail/demo.html` → 「页面是验证页 / JS 壳…」+ 提示 `export DSH_LEARN_COOKIE='…'` 再试，或改用截图与粘正文 |
| 匹配度加权 | API 用例断言：刚入库的岗位出现在推荐里、`why` 至少两条、含「硬要求对应的题」（存了硬要求就走加权） |
| 核心用例 | `test/flow.test.mjs`：覆盖 50% 且老数据写「没存硬要求」；存了硬要求的岗位分数与纯覆盖**不同**且依据里有硬要求那项 |
| 界面护栏 | 流程页「按链接抓 JD」按钮 + `action=collect url` 的断言 |
| 原生自检 | **150 → 153 项全过**：空链接要报错、按链接抓取能入库并带分析、收尾删记录 |
| `node --test` | **408/408** |

### 还剩什么

- 推荐仍不看薪资 / 地点 / 时间（JD 里这些字段目前只是文本，没有结构化）——下一步可以在 `understand.mjs` 里补 `location` / `salary` / `postedAt` 抽取，再进排序；

## 5.164 针对单个岗位的投递材料 + 岗位属性（地点/薪资/发布时间）进筛选（第 161 轮 / 共 250 轮）

上一轮留的两条边界：推荐不看薪资/地点/时间、投递只有通用要点。这轮各补齐。

### 岗位属性抽取：地点 / 薪资 / 发布时间 / 是否远程

`understand.mjs` 新增三个抽取器（规则化、可解释、离线）：

| 字段 | 规则 | 实测 |
| --- | --- | --- |
| `location` | 「工作地点/办公地点/base」标签，或城市词表（36 个），或「远程/居家/remote」 | `深圳` |

3. **差异自陈**：还没练到的方向 + 具体要补的题 + `flow build` 的补练计划（主动说比被问到好）；
4. **投递动作**：岗位链接（dsh-learn 不代填表单）+ 投完 `flow apply` 记状态。

## 5.165 推荐筛选落到三端界面 + 发布时间参与排序（第 162 轮 / 共 250 轮）

### 先纠正上一轮的一处文档漂移

5.164 里写了「界面里对应「按匹配度算一遍」下方的筛选输入」——**当时并不成立**：地点/薪资/远程那一轮只做到了 CLI 与 core，

### 筛选真正接到三端

| 端 | 这轮新增 |

### 薪资改成区间重叠，不再只卡下限

### 二、被项目的两条口径教育（都记进注释）

### 一、缺陷与实测

`progress.json` 早就用「追加日志 + 归档」规避了并发覆盖；**`jobs.json` 一直是 `readJobs() → 改 → writeJobs()`**。写单文件是原子的，但整段读-改-写不是：

| --- | --- | --- |
| 20 个并发写入者 | 只剩 **7** 条（丢 13） | **20/20** |
| 40 个并发写入者 | 只剩 **16** 条 | 40/40 |
| 200 / 400 个 | —— | **200/200、400/400，且 0 个进程失败** |

### 二、修复过程：四版，每版都被实测打回

| 版本 | 做法 | 实测结果 | 教训 |
| --- | --- | --- | --- |
| 1 | 追加操作日志，写入时与当前视图算差量 | 仍丢：调用方基于**陈旧读取**拼出数组，差量把别人的记录当成「删除」 | 全量替换语义 + 并发 = 必然丢；改成 **upsert 语义 + 显式 `deleteJobRecord`** |
| 2 | 归档加锁（只串行归档） | 80 个写入者丢 5：两个进程同时归档互相覆盖 | 归档必须串行 |
| 3 | 修「existsSync → readFileSync」的 TOCTOU | 之前 `jobs.ndjson` 被归档方 rename 走时直接 **ENOENT 崩溃** | 读不到就当空，别先探存在 |
| 4 | 归档改「rename 抢 inode + 补读」 | 200/400 仍偶发丢 1–2 条：补读与 unlink 之间还能追加；且「拿不到锁就裸写」的兜底正好和归档打架 | **写路径也持锁**、去掉裸写兜底、只写「有变化」的记录（阈值 50→500，减少抢锁） |

最终形态：

```
写入：withStoreLock( 追加操作(upsert/delete) → 超过阈值则归档 )
读取：快照(jobs.json) + 日志回放(jobs.ndjson)，操作幂等
锁  ：O_EXCL 锁文件；陈旧锁（>5s）可抢占；等不到就报错而不是裸写
```

### 三、顺带修掉的同类隐患

- **进度记录也有同样的归档窗口**：`takeJournal()` 先把日志 rename 走再写快照，期间并发读者看不到这些记录 → 改成锁内「先写快照、再处理日志」；
- **读日志的 TOCTOU**：`readJournalFile`/`journalSize` 也是先 `existsSync` 再读 → 并发下 ENOENT；一并改成「读失败即空」。

### 一、设计：完全复用既有只读白名单，不新开执行面

### 一、掌握度：可复算、排序可解释

```

## 5.200 第 26 轮：知识点分析的性能优化（实测 -35%）+ 文档补强（第 197 轮 / 共 250 轮）

目标里还有「性能与文案优化」这一项，这轮挑了个**三端共用、可精确测量**的热点：项目体检（doctor）里的知识点分析。

### 一、先量再改

分步计时（115 份来源 / 约 9.5 万字）：`listProjects` 10ms、读原文 31ms、**`analyzeText` 77ms**——瓶颈很明确。

根因：`matcher()` 每次调用都 `new RegExp`，而一次体检要跑 167 个知识点 × 957 条规则 × 115 份来源 ≈ **3.8 万次**正则构造。

### 二、做法与实测

给 matcher 加**编译缓存**（同一条 pattern 只编译一次；这些正则都不带 g 标志，共享实例没有 lastIndex 状态问题）：

| 场景 | 优化前 | 优化后 |
| --- | --- | --- |
| analyzeText 全部来源（首次，含编译 957 条） | 77ms | **53ms** |
| analyzeText 全部来源（再次，编译缓存命中） | 77ms | **35ms** |
| `doctor` 冷启动 | 133ms | **86ms（-35%）** |
| `doctor` 第二次 | 74ms | **53ms（-28%）** |

### 三、被实测否决的优化（如实记录）

我还试了「先 `indexOf` 再 `exec`」的前置过滤（字面量词不存在就跳过正则），直觉上应该更快——**实测更慢：55ms vs 37ms**。原因是逐条扫长文本并不比 V8 优化过的字面量正则便宜，而构建小写副本还额外花钱。**已回退**，只保留真正有效的编译缓存。
