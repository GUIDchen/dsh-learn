### 二、发现 1：拆分暴露了 `TaskDetail.body` 的**类型检查超时**

搬完第一次构建直接失败，报的却是 `main.swift` 里「VerdictPanel 没有 frame / 缺 store 参数」——典型的**连锁假错**。单独对 UI 文件做 typecheck 才看到真话：

```
NativeUI.swift:1917: error: the compiler is unable to type-check this expression
                      in reasonable time; try breaking up the expression into distinct sub-expressions
```

`TaskDetail.body` 是一个上百行的巨型视图构建器，行号一挪就压过了编译器的推断预算。按它自己的建议拆成三个 `@ViewBuilder`：`detailHeader`（题目头部）/ `answerArea`（作答区）/ `emptyState`（空状态）。**这同时解释了上一轮整页拆分为什么会失败**——同一个超时，换个文件就换个地方报。

### 三、发现 2：我自己新文件漏了 `import SwiftUI`

`VerdictPanel.swift` 的头注释写好了、`import` 忘了。漏 import 时 Swift 不报「找不到 View」，而是把该文件所有类型判为不满足协议，**报错全落在使用处**（因此前面那两轮假错也有它一份）。补上一行后编译通过。**教训：新建 Swift 文件先写 import，再看错误。**

### 四、发现 3：编译耗时没有变快（拒绝自我安慰的度量）

我本来准备写「拆分让编译更快」，于是做了 A/B（同一次会话、同一台机器）：

| 配置 | `-O` 编译耗时 |
| --- | --- |
| 拆出 `VerdictPanel.swift`（3 文件参与） | **63.6s** |
| 合回单文件（只保留 body 拆分） | **69.9s** |
| （之前记的「拆分前 54s」） | 单次测量、含变量，不作为基线 |

结论：**耗时属噪声级差异**，不作为这轮的收益。真实收益是：消除那个会导致编译失败的超时、行数下降、支撑面板有了独立文件可以继续长。

### 二、只有浏览器能抓到的真 bug：模块初始化顺序（TDZ）

单元用例、体量守卫、模块化守卫全绿之后，浏览器一打开就是**整页空白、0 道题**：

```
ReferenceError: Cannot access 'panels' before initialization
    at http://127.0.0.1:8911/app.mjs:989:43
```

根因：`app.mjs` 中间有一段**顶层语句**（`$('drillMode').addEventListener('change', panels.loadDrill)`），它求值时 `const panels` 还没初始化 → 暂时性死区抛错 → **模块后续代码全部不执行**（所以题目列表也是空的）。

修法：把初始化放在 `$` 与 `state` 之后、任何顶层引用之前（两处都是 `const`，顺序错一步都不行），并在代码里写明这条约束。第一次修的时候我只挪到了 `state` 后面，又被 `$` 挡了一次——**同一个坑踩了两次**，所以最终把「必须在 $ 与 state 之后、必须在任何顶层引用之前」写进了注释。

这条经验直接支撑 C 类第一项：**这类问题只有真实浏览器会暴露**，所以要把 CDP 冒烟从「每轮手写 /tmp 脚本」搬到仓库里（`scripts/e2e-web.mjs`），让每轮都能一条命令跑到。
