## 5.8 存储并发安全（第 3 轮 / 共 20 轮）

### 问题

原来的 record() 是"读整个 JSON → push → 覆盖写"：CLI、网页、agent 同时提交时后写的会把先写的覆盖掉；进程写一半被杀会留下半截 JSON，下次读取直接当空处理——进度会**静默丢失**。

### 改法

| 环节 | 做法 |
| --- | --- |
| 单条记录 | appendFileSync 追加一行到 progress.ndjson（O_APPEND 单行写入原子），不做读-改-写 |
| 快照落盘 | 写 progress.json.tmp-<pid> 再 rename 覆盖，顺带把上一版留成 progress.json.bak |
| 归档 | 日志攒到 200 条时，抢到 rename 的进程把日志改名拿走 → 并进快照 → 删除；期间新写入落到新日志，不会丢 |
| 快照损坏 | 自动回退 .bak，坏文件改名 progress.json.corrupt-<时间> 留档 |
| 日志半行 | 解析时忽略并计数，progress 命令会提示"有 N 行无法解析" |
| 观测 | storageHealth() 暴露路径、记录数、日志字节数、坏行数、是否从备份恢复；CLI 与 /api/progress 都会带上 |

### 证据

- 新增 test/store.test.mjs 8 个用例，其中**并发用例真的 spawn 8 个 node 进程各写 5 条**：最终读到 40 条，一条不丢。
- scripts/verify.sh 增加一节：4 个进程并发执行 node src/cli.mjs check，之后 board 里必须正好 4 个客户端 —— 实测通过。
- 用例还覆盖：半行容忍、快照损坏回退并留档、归档后日志清空、导入两次只生效一次。
- **本轮修掉的真 Bug**：reset() 原来只清快照，日志里的待归档记录会在下次读取时"复活"，现在 reset 会连日志一起丢弃。
- node --test 136/136；scripts/verify.sh 36/36 exit 0。

## 5.9 白名单与题库对账（第 4 轮 / 共 20 轮）

### 问题

白名单是唯一的安全边界，但它原来只是一串匿名正则：题库新增验证项时可能忘记加白名单（学员点了"只读验证"却永远跑不了），反过来白名单里也会攒下没人用的条目——**攻击面悄悄变大**。这正是第 1 轮审阅时记下的 ponytail 债务。

### 改法

- 白名单条目结构化：每条 { id, family, examples, 正则 }，例如 { id: 'docker-ps', family: 'Docker 只读', examples: ['docker ps', 'docker ps -a'] }。
- 新增 auditWhitelist(tasks)：把题库里所有 verify（含平台变体）与白名单对账，输出
  entries（每条被谁使用）、unused（没人用的条目）、blocked（题库声明了但白名单没有）、tasksWithoutVerify、mustStayBlocked（必须继续被拒绝的命令清单）、leaked（本该拒绝却被放行）、ok。
- 工具自身内部用到的命令（probe 的 uname/sw_vers/docker version/context ls、容器后端的 docker info、测试里的 node -v）登记为 SYSTEM_USES，避免审计误报。
- 新命令 node src/cli.mjs security whitelist [--json]：对账失败以退出码 1 结束；CI 与 scripts/verify.sh 都跑它。

### 顺手清掉的真问题

审计第一次运行就发现 6 条白名单没人用：sw_vers / node -v / docker info 实际是工具内部要用的（登记为 SYSTEM_USES 后保留），而
docker compose version、docker images、kubectl cluster-info 确实没有使用者——**已删除**，需要时再加（加的时候审计会提醒同时加用它的题）。

### 证据

- 新增 test/whitelist.test.mjs 6 个用例：每条模式必须首尾锚定且带示例与归属；MUST_STAY_BLOCKED 里的危险命令（rm -rf /、docker volume rm、kubectl delete、git push --force 等）必须继续被拒绝；含 ; | > && 元字符的命令必须拒绝；对账必须无阻塞、无闲置、无泄漏；对账能识别"题库声明但白名单没有"的命令。
- 现在"白名单里不允许存在没人用的条目"是一条硬断言——白名单不会再悄悄腐烂。
- node --test 143/143；scripts/verify.sh 37/37 exit 0。

## 5.10 执行后端边界与失败路径（第 5 轮 / 共 20 轮）

### 目标

runners.mjs 的分支覆盖只有 47.76%：成功路径有人测，**失败路径没人测**——而失败路径恰恰是学员最容易撞上的地方（守护进程没起、镜像拉不到、远端 agent 连不上、命令超时）。这一轮把失败路径逐个钉住，顺手修掉了三个真 Bug。

### 新增测试（test/runners-edge.test.mjs，9 个用例）

| 场景 | 断言 |
| --- | --- |
| 本地命令超时 | 明确报"命令超时：超过 Nms 仍未结束"，而不是"exit null" |
| 没有验证项 / 未知后端 | 可读结论，不抛异常 |
| runVerify 叠加超时与白名单 | 保持超时原因不被"输出未匹配"覆盖 |
| 容器后端 dry-run / 白名单 / 非法镜像名 | 三条路径各有明确说明（守护进程不可用时降级说明，可用时带回 docker 报错） |
| 容器真实执行 | 本机有镜像时真在容器里跑 uname -s，必须输出 Linux |
| 远端缺 endpoint / 连不上 / agent 500 / 返回非 JSON | 每种都给出可读原因，并带上 status |
| agent 非法请求 | 坏 JSON → 400；超大请求体 → 413；未知路径 → 404；GET /agent/exec → 404 |

### 修掉的真 Bug

1. **超时结论被下游覆盖**：exec.runVerify 拿到"命令超时"后又用"输出未匹配预期"覆盖了 reason，学员看不到"超时"两个字。现在 timedOut / exitCode === null 时直接返回原结论。
2. **agent 收到超大请求体时直接把 socket 断掉**（req.destroy()），客户端只看到 socket closed 或干脆挂住——这和网页版服务端是同一个坑，agent 里没跟着修。现在与 web 服务端一致：标记已拒绝、继续读完剩余数据、回 413（并带 Connection: close）。
3. **测试里的 keep-alive 泄漏**：关掉临时 http 服务时不断开保活连接，undici 的 socket 会把"other side closed"错误算到下一个测试头上，还会让测试文件永不退出。现在关闭前调用 closeAllConnections()，请求带 Connection: close，并用 t.after 保证断言失败也会回收服务。

### 覆盖率变化

| 文件 | 行覆盖 | 分支覆盖 |
| --- | --- | --- |
| runners.mjs | 92.31% → **97.80%** | 47.76% → **67.57%** |
| exec.mjs | 97.06% → **98.13%** | 77.61% → **83.95%** |
| 整体 | 90.10% → **90.98%** | 72.06% → **74.49%** |

剩余未覆盖的 runners 分支（82-83、115-116）需要"守护进程在线 / 远端 agent 在线"的可用性分支，已由端到端脚本覆盖。

## 5.11 覆盖率门槛与趋势（第 6 轮 / 共 20 轮）

### 问题

覆盖率之前只是"跑一次看一眼"的数字：没有基线、没有门槛，改坏了也没人知道。

### 改法

- 新增 scripts/coverage.mjs：跑一遍测试拿 lcov（node --test --experimental-test-coverage --test-reporter=lcov），解析成每文件的行/分支/函数覆盖，按基线比对。

## 5.12 复习队列 / 学习目标 / 题目笔记（第 7 轮 / 共 20 轮）

### 复习队列（间隔重复，规则刻意简单可解释）

- 未通过 → 1 天后重来；一次通过且没错过 → 7 天；错过之后再通过 → 3 天；连续通过 n 次（n≥2）按 7n 天，上限 30 天。

- dailyPick 的优先级随之调整为：该复习的题 → 练过但没满分 → 完全没练过。
- CLI：node src/cli.mjs review [--limit] [--track] [--json]，输出"该复习"与"之后到期"两段。

## 5.21 执行器挂死根治：异步 + 进程组 + 可注入 seam（第 16 轮 / 共 20 轮）

### 问题是真实发生的

第 16 轮跑到一半，整个测试进程卡死 37 分钟。ps 一看：docker info 已经挂了 15 分钟，而测试还在等它。

根因不在 Docker，在执行器的实现上：runReadonlyCommand 用 spawnSync + shell: true 跑命令，超时只杀掉直接子进程（shell），被 shell 包住的 docker/kubectl 会活下来继续握着 stdout 管道，而 spawnSync 要等管道关闭才返回 —— 于是"超时"永远不会发生。

### 改法

- 执行器改成异步 spawn + detached 进程组：超时按进程组 SIGKILL（process.kill(-pid)），一次带走 shell 与它的所有后代；输出超过 64 KB 直接截断并终止（只读命令不该产生这么大的输出）。
- killSignal 统一用 SIGKILL：SIGTERM 遇到不理会它的命令会一直等下去，超时就不再是超时。
- 守护进程探活不再走 shell 包装，直接 spawn docker info。

### 效果

| 场景 | 之前 | 现在 |
| --- | --- | --- |
| 守护进程卡死（socket 在但无响应） | 整个 CLI 挂住不返回（实测 15 分钟以上） | 5 秒内输出「docker info 在 5000ms 内没有返回（守护进程无响应）」 |
| 守护进程没起 | 正常降级 | 正常降级，并把 docker 的原始报错一并带上 |
| 命令输出失控 | 无上限 | 超过 64 KB 截断并终止 |

### 顺带把"没有 Docker 的机器上测不到"的洞补上

镜像预检 ensureImage 与容器内执行 runInImage 抽成可注入 exec 的函数，"守护进程可用 → 镜像本地已有 → 容器内跑通"这条主路径现在用注入的执行器就能覆盖，不再依赖本机有没有 Docker。覆盖率反而从 92.6% 回到 93.8%（分支 80.1%），25 个文件全部达标。

### 证据

- node --test 206/206
- node scripts/coverage.mjs → 覆盖率门槛通过（25 个文件），行 93.8% / 分支 80.1%
- node src/cli.mjs runners → 1.2 秒返回，docker 一行给出中文降级说明

## 5.25 真正把"离线也能练"跑通（第 21 轮 / 共 20 轮，追加轮）

这一轮不是加功能，而是去验证一句已经写在 README 里的承诺：断网也能练。结果发现这句话在这个环境里根本不成立。

### 现场

用真实浏览器打开页面，检查 Service Worker 状态：

    navigator.serviceWorker.getRegistrations()   → []      （一个注册都没有）
    caches.keys()                                → []      （缓存是空的）
    手动 navigator.serviceWorker.register('/sw.js') → 成功、active、controlled

也就是说 sw.js 本身没问题，是页面压根没去注册它。

### 根因一：注册挂在 load 上，而脚本晚于 load 执行

app.mjs 结尾写的是 window.addEventListener('load', ...) 里注册。实测这一页的 load 事件在 18ms 就结束了，模块脚本执行时监听器已经错过，注册永远不会发生；而 .catch(function () {}) 把失败也吞掉了，所以从第 1 轮到现在都没人发现。修法：document.readyState 已经是 complete 就立刻注册，否则再挂 load；失败改为 console.warn 留痕。

### 根因二：离线重开页面只剩空壳

判定内核确实被 Service Worker 缓存了，但题目、规则、参考命令都来自 /api/bootstrap。断网重开时接口是 503，页面里 0 道题——"能离线练"实际只在不刷新的前提下成立。修法：bootstrap 成功后把整份数据（含完整判定规则）存进 localStorage，接口失败时用它兜底，并在顶部写明"离线：题库来自 YYYY-MM-DD HH:MM 的缓存"。

### 根因三：顶部徽标一直显示"在线"

在线状态原来只在 offline 事件里翻转，服务端挂了不会变。修法：抽 markOffline / markOnline，在 api() 这一处统一翻转（请求失败或返回非 2xx 就算离线，成功就算在线），徽标随请求结果实时变化。

### 实测（真实浏览器，服务端真停真起）

| 步骤 | 结果 |
| --- | --- |
| 在线打开一次 | 95 道题，bootstrap 已缓存 |
| 停掉服务端后重开页面 | 仍是 95 道题（题库来自缓存），徽标变「离线 · 本地判定」 |
| 离线提交 uname -s | 「判定：通过（100 分）」，队列 1 条 |
| 服务端起回来并重开 | 队列 0 条，徽标回「在线」，提交历史里出现 09-26 01:50:16 linux.platform-probe 通过（100）uname -s |

### 证据

- node --test 207/207（新增 page.test.mjs 离线能力断言：注册时机、题库缓存、在线状态统一翻转、缓存来源提示）

## 5.26 界面重叠根治 + 三栏在窄窗口的表现（第 22 轮 / 共 20 轮，追加轮）

### 先复现，再改

用户报"左栏和中间有重叠"。直接在 1280px 窗口里量：三栏矩形互不相交，也没有横向溢出——换不来结论，就让页面在 iframe 里按 10 档宽度各渲染一遍（iframe 的媒体查询按自己的宽度算），逐档量 getBoundingClientRect 与"子元素是否越出所属栏"。

量出来的事实：

| 宽度 | 现象 |
| --- | --- |
| ≥1201px | 三栏正常，左右栏吸顶 |
| 820–1200px | 两栏模式；左右两栏仍是 sticky + max-height: calc(100vh - 90px)，题目列表变成一个小滚动框 |
| ≤780px | 单栏模式，但左栏被压成 300px 的滚动框，内容要在一个小窗口里翻 |

### 改法（都是"让格子绝不会被内容撑破"这一类）

- 网格轨道改成 minmax(200px, 272px) / minmax(0, 1fr) / minmax(0, 360px)，并给三栏加 min-width: 0：网格子项默认 min-width: auto，长命令与长路径会把列撑出轨道，多出来的部分就压在相邻栏上——这是"重叠"的典型成因。
- 长内容一律换行：task-item / cmdline / pre / td / th / muted 加 overflow-wrap: anywhere，pre 加 max-width: 100%。
- 吸顶只在真正放得下的宽度生效：≤1200px 时左右栏改为 static，不再和中间栏的滚动内容抢视觉层级。
- 单栏模式取消 300px 夹层，题目列表整页顺序往下排。

### 验证

10 档宽度（1440/1280/1180/1000/900/820/780/640/520/480）逐档量：三栏矩形零相交、子元素零越界、页面零横向溢出。回归断言进 test/page.test.mjs（轨道写法、min-width: 0、overflow-wrap、窄屏取消吸顶、不再有 300px 夹层）。

## 5.35 离线外壳加固：缓存桶随版本走、预缓存不再一把梭（第 31 轮 / 共 50 轮）

### 先审离线外壳这条链路，找到两个真问题

1. 缓存名写死 dsh-learn-shell-v1：发版之后旧外壳还在缓存里，只能靠「命中缓存 + 后台悄悄刷新，下次打开才新」来兜底——用户第一次看到的总是旧版，而且旧资源永远不会被主动清理。
2. 预缓存用 cache.addAll(SHELL)：这是全有或全无的语义，任何一个资源 404 都会让整个安装失败，SW 永远不激活，离线能力整块消失（而且失败是静默的）。

### 改法

- 缓存名改成 dsh-learn-shell-__VERSION__，由服务端在发送 sw.js 时替换成 package.json 里的真实版本（static.mjs 的 APP_VERSION）。发版即换桶，旧缓存由 activate 阶段清掉。
- 预缓存改成逐个 fetch + cache.put，单个失败只 console.warn，不影响其余资源与安装，并把失败路径写进告警便于排查。
- 断网且未缓存时按请求类型分流：导航请求回落到外壳首页，其他资源如实返回 503（不再一律回落 index.html，避免把 HTML 当脚本用）。

### 排障记录（顺手抓到的坑）

第一次下发 sw.js 时版本被替换成了 dev：APP_VERSION 的计算被放在 const HERE = ... 之前，TDZ 异常进了 catch 兜底。教训是兜底值会悄悄吞掉版本语义——现在测试直接断言「缓存名必须等于当前 package.json 版本」，写成 dev 就会红。

- easy：≤3 要素，且没有 forbid、没有 variants；
- medium：4–5 要素，或带 forbid / variants 的 ≤3 要素题；
- hard：≥6 要素；或 ≥5 要素且含 block 级禁止项。

按这个口径刷 47 个包：简单 22 / 中等 265 / 困难 18。level 存 ASCII（easy/medium/hard），客户端渲染中文，这样既能进 URL、又不用中英混排在 JSON 里。不写 level 视为 medium——外部包是照旧能加载的。

### 一条链改到底

schema 校验先拦住脏值（level 只能是 easy/medium/hard，写「超难」加载即报错），然后同一条 level 贯穿三层：

- 内核：schema.mjs 出 LEVELS / LEVEL_LABELS，tasks.mjs 出 levelLabel() / levelStats() / listTasksByLevel()；
- CLI：list --level=hard（非法值退出码 2），列表打 [轨道·难度] + 难度分布一行；show 带 level/levelLabel；
- Web：/api/bootstrap 下发 levels / levelLabels 与每题 level，左栏多一组难度筛选（全部/简单/中等/困难），列表项难度标签用点线/虚线/实线粗细区分，不靠颜色也能分辨。

### 文档也钉在运行时上

难度分布写进 README 一句，同时 consistency 用例断言它必须等于运行时统计——以后调难度忘了改文档，测试直接红。

## 5.47 macOS 端改成原生客户端（第 43 轮 / 共 250 轮）

之前 macOS 端是 WKWebView 外壳：窗口里装的还是网页版。这一轮把它换成真的原生客户端——AppKit + SwiftUI，
窗口里没有一个 HTML 元素；判定引擎仍然是项目目录里的同一份 Node 服务，客户端只说 HTTP。

### 三个新文件与一份自检

| 文件 | 职责 |
| --- | --- |
| app/macos/Engine.swift | 找 node / 项目目录、挑空闲端口拉起引擎、bootstrap / check / history / progress 的 HTTP 客户端与模型 |
| app/macos/NativeUI.swift | 原生三栏界面：左栏筛选题单、中栏题目与作答、右栏判定结果；状态集中在 Store |
| app/macos/main.swift | 窗口、菜单（编辑菜单留着，文本框要靠响应链拿 ⌘C/⌘V）、App Nap 抑制、退出回收引擎 |
| app/macos/selftest.swift | 客户端接口自检：跑真实链路，verify.sh 每次编译并执行（进度写临时 HOME，不碰真实进度） |

### 真机实测踩出来的三个坑

1. **靠管道拿地址会随机失败。** 原来（网页壳版本）靠解析子进程 stdout 里的 DSH_LEARN_URL 拿端口。
   实测在 GUI 进程里，管道读端的回调会被系统压后二十多秒；更糟的是管道缓冲区只有 16 KB，
   子进程一写满就卡在 write 上，永远走不到 listen()——表现成"引擎起不来"，而且时好时坏。
   改法：端口由客户端自己 bind 一个空闲端口再交给引擎，地址立刻已知，只剩轮询接口；引擎输出改直接写日志文件
   （以 O_APPEND 打开，父子进程各写各的，不会互相盖），彻底不依赖管道时序。
2. **查询串被转义。** /api/history 用 URL.appendingPathComponent 拼，问号被转成 %3F，
   于是右栏"这道题的最近记录"永远是空的（接口 404，但页面只表现为"没有记录"）。
   改法：统一用 URLComponents 拼 path + queryItems。
3. **后台被降频。** 窗口不在前台时系统 App Nap 会压后定时器与队列，8 秒就判"引擎没起来"。
   改法：applicationDidFinishLaunching 里 beginActivity(.userInitiated)，启动等待放宽到 60 秒，
   失败时把最后一次的真实错误（含 NSError 详情）直接显示在窗口里，并给"重试 / 打开日志"。重试会先收掉上一次留下的引擎，不再叠进程。

4. **引擎根本起不来：macOS「文稿文件夹」权限。** 项目在 ~/Documents 下，从 GUI 进程派生的引擎（没有终端那份授权）
   调 getcwd() / open() 时会卡在系统裁决上——同一行命令从终端跑却秒过。用 launchctl submit 起一个同样"没有终端授权"的进程复现：
   cwd 在 ~/Documents 里时 `process.cwd()` 一直不返回，cwd 在 /tmp 时 0 ms 返回；采样卡住的引擎，栈停在
   `__private_getcwd → open$NOCANCEL` 与 `uv_fs_open`。这不是客户端的逻辑 bug，但客户端必须绕开它，于是三处改：
   - **引擎打进 App**（Contents/Resources/engine，含 src / packs / web / package.json）：装到 ~/Applications 后完全不读项目目录；
   - **引擎的 cwd 设为 /**：不再让子进程的 getcwd 走到受保护目录；
   - 启动超时时的报错带上可操作的说明（装到非受保护目录 / 给 App 打开文稿访问 / 移出 ~/Documents），而不是只甩一段 NSError。

右栏：分数、判定、进度条、与历史最好对比、已命中片段、缺失项、提示与参考答案、这道题的最近记录。
