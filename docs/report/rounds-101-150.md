### 为什么困难题要「六步」而不是「六条要素」

本仓的难度口径是机器判的：要素 ≥ 6 或（≥ 5 且含 block 级禁止项）才算困难。所以想标困难，就得真的写出一条长命令——
比如把「起容器」写成「后台 + 命名 + 重启策略 + 健康检查三件套」，这是生产里真实会写的样子；
把简单命令拆成六条要求则过不了人工复核，也骗不过口径（口径看的是要素本身）。

## 5.109 进度写不进去时：判定要给出来，且不许假装成功（第 106 轮 / 共 250 轮）

这轮换一类环境试：**进度目录不可写**（只读挂载、权限没给对、磁盘满）。

### 发现的形态

`DSH_LEARN_HOME` 指向一个 `chmod 500` 的目录时，`check` 的表现是：
判定算完了、**输出里一个字的反馈都没有**，只有一行 `命令执行失败：EACCES …`——用户既看不到自己得分，
也不知道记录没保存。判定本身是用户要的东西，不该因为落盘失败而消失。

（顺带记一次测量事故：第一次量退出码时我用了 `node … | tail -3` 再取 `$?`，
拿到的是 `tail` 的 0。严谨地重测后，退出码其实是 **1**——与第 97 轮的 `reset_config` 那次同一类错误：**管道会吃掉退出码**。）

### 改法

- `check` 里把 `record()` 包起来：写失败**不吞掉判定**，照常打印任务/平台/判定/反馈/历史对比，
  然后往 stderr 写「这次没记上：<原始错误>（判定结果不受影响；检查 … 的写权限或磁盘空间）」，**退出码 1**；
- JSON 输出新增 `saved` / `saveError` 两个字段，脚本能直接判断有没有落盘；
- 入口的兜底错误处理：识别 `EACCES/EPERM/EROFS/ENOSPC` 时补一句「检查 DSH_LEARN_HOME 目录的写权限与磁盘空间」。

### 实测

| 场景 | 结果 |
| --- | --- |
| 只读 HOME 下 `check`（正确命令） | stdout 照常给出「判定：通过（100 分）… 已命中 5 / 5」 |
| 同一命令的 stderr | 「这次没记上：EACCES …」+「检查 … 的写权限或磁盘空间」 |
| 退出码 | **1**（脚本能发现记录没落盘） |
| 负向验证 | 把提示文案改掉后测试立刻变红，说明用例真的在拦这件事 |

## 5.110 项目元数据坏掉时：宁可拒绝，也不许静默覆盖（第 107 轮 / 共 250 轮）

这轮盯的是**数据丢失**这一类缺陷：`~/.dsh-learn/projects/<名字>/project.json` 是项目里所有来源的台账
（哪次的截图、哪次的仓库、解析出多少知识点）。它一旦坏掉（写盘被打断、手改错一个字符、磁盘满写了一半），
旧代码的表现是：**当作「项目不存在」，直接重建一个空台账**。

### 实测出来的形态

    $ node src/cli.mjs project add demo-broken --text "docker run -d --name web nginx"
    （无任何提示）退出码 0
    损坏前来源数: 2  →  之后: 1

原来的两条来源记录被一份新台账顶掉，且**一个字都没提示**。这是最坏的一类 bug：数据没了，
用户还以为只是「又加了一条」。

### 改法（三层一起拦，共用同一份判断）

- **core**：新增 `projectState()`，把「没建过 / 正常 / **元数据损坏**」分成三态——损坏必须与「没建过」分开，
  否则任何写入都会把它当空目录重建。`createProject()` 与 `ingestIntoProject()` 在损坏时返回
  `{ ok:false, corrupted:true, reason }`，**不碰坏文件**；
- **CLI**：`ensureProject()` 打印「… 不是合法 JSON，不敢覆盖。」+「先备份或修好它，或者换一个项目名再试
  （旧文件的来源台账还在里面）」，`project add` / `project init` 均以 **退出码 3** 结束；
- **网页版**：`/api/project` 的 init / 收来源两条路径都返回 **400 + { corrupted:true }**，与 CLI 共用同一份 core 判断；
- **macOS 原生端**：顺手修掉一个把业务错误讲成「引擎没起来」的老毛病——`Engine.swift` 的 `request()` 以前把
  任何非 200 都套上「引擎没起来：… + 文稿文件夹权限」的长文案，于是「项目元数据损坏，不敢覆盖」在 App 里
  被导去查隐私设置。现在带 `error` 字段的非 200 走新的 `EngineError.api`，原样显示服务端那一句。

坏文件**原字节保留**，人才能自己备份、修 JSON 或换个名字继续。

### 实测

| 场景 | 结果 |
| --- | --- |
| 2 条来源的项目 → 把 project.json 改成 `not json at all` → `project add` | 退出码 **3**，stderr 给出原因与两条建议 |
| 同一状态下 `project init` | 退出码 **3**，同样不覆盖 |
| 网页版 `POST /api/project`（收文字） | **HTTP 400**，`corrupted:true`，error 为「项目元数据损坏，不敢覆盖：…」 |
| 三次操作之后 | `project.json` 仍是 `not json at all`（字节未变） |
| 原生 App 收来源（同一损坏状态） | 抛出「项目元数据损坏，不敢覆盖：…」，**不再**出现「文稿文件夹权限」那段排查文案 |
| 负向验证 | 用例断言「字节不许变」与 `corrupted === true`，改回旧行为立刻变红 |

- 新增测试：test/project.test.mjs「项目元数据损坏：拒绝覆盖，原文件字节不动」、

## 5.112 偶发红了一次的测试：同毫秒的两次练习被判成「重复」丢了（第 109 轮 / 共 250 轮）

这轮是被自己的测试逼出来的：跑全量测试与 `verify.sh` 时，「check 命令：第二次以后给出与历史最好的对比」
偶发失败，而单独跑它又总是过。

### 复现

把那条用例连跑 12 次（每次新进程、新临时 HOME）：**第 8 次红了**，失败断言是：

    换平台仍然记在同一条进度里
    expected /累计第 5 次练习/  actual 「累计第 4 次练习」

根因在存储层，不在用例：记录的去重键是**字段组合** `(client, taskId, at, score, verdict)`，
而 `at` 只有毫秒精度。同一毫秒内提交两次「同题、同分、同判定」的答案（机器快的时候就会出现），
第二条会被 `dedupe()` 当成重复**静默丢掉**——用户看到的是「累计第 4 次」，少了一次。

### 改法

身份不该从内容里猜，应该在写入时生成：`record()` 给每条记录加 `randomUUID()` 作为 `id`，
`recordKey()` 优先用 `id`；**老记录（备份文件里没有 id 的）继续按字段组合去重**，
所以「导出一份备份、导入两次只生效一次」的幂等性一点没变。

### 实测

| 检查 | 结果 |
| --- | --- |
| 同毫秒 5 次相同成绩（新路径） | 5 条记录，一条不少 |
| 老备份（无 id）导入两次 | 第一次 added=1，第二次 added=0（幂等性保持） |
| 命令行连交 5 次同题满分 | 依次打印「这是第一次练」→「累计第 2」…「累计第 5 次练习」 |
| 修前 vs 修后跑同一条用例 | 修前 12 次里失败 1 次；修后 **14 次全过** |
| 负向验证 | 新用例断言「两条相同字段的记录必须是 2 条」，恢复旧的字段组合去重立刻变红 |

### 证据

- 改动：src/store.mjs（`record()` 生成 id、`recordKey()` 以 id 为准）
- 新增测试：test/store.test.mjs「同一毫秒的两次相同成绩不会被当成重复丢掉」
- node --test 全绿（312 项）；bash scripts/verify.sh **PASS 72 / FAIL 0**

## 5.114 一个请求卡住整个服务端：brotli 默认质量实测 1.1 秒（第 111 轮 / 共 250 轮）

这轮量的是页面加载。`window.__dshPerf` 报出的第一个数字就不对劲：**bootstrapMs 936 ms**、
firstListMs 942 ms——本机、预热过的服务端、568 道题的题库，凭什么要将近一秒。

### 定位

先怀疑服务端算得慢，量了一遍：把 568 道题 resolve + stringify 一共 **5 ms**。不是算法的问题。
于是逐编码量同一个接口：

| 编码 | 服务端 TTFB | 传输体积 |
| --- | --- | --- |
| identity | **12 ms** | 490 KB |
| gzip | **24 ms** | 139 KB |
| brotli | **1130 ms** | 110 KB |

根因是 `brotliCompressSync(buffer)` 用了 zlib 的默认质量 11：为了少传 29 KB，
每次请求花掉 1.1 秒 CPU。更糟的是它是**同步**压缩——Node 是单线程，这 1.1 秒里
页面同时打的 /api/progress、/api/drill、/api/daily… 全在排队。

### 改法（按曲线的拐点选，不凭感觉）

实测这条真实正文的 brotli 质量曲线：

| 质量 | 耗时 | 体积 |
| --- | --- | --- |
| q11（默认） | 1055 ms | 110 KB |
| q9 | 39 ms | 118 KB |
| **q6（选它）** | **16 ms** | **121 KB** |
| q4 | 6 ms | 138 KB |
| gzip l6 | 13 ms | 139 KB |

再加一层「同一份正文只压一次」的缓存（SHA-1 做键，最多留 12 份）：bootstrap 按平台是固定正文，
app.mjs / index.html 也是，每次刷新重压纯属浪费。

### 实测（改前 → 改后）

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| /api/bootstrap 的 br 响应 | 1130 ms / 110 KB | **20 ms** / 121 KB |
| 同一份正文第二次起（压缩缓存） | 1080 ms | **4.7 ms** |
| 页面 `__dshPerf.bootstrapMs` | 936 ms | **17 ms** |
| 页面 `__dshPerf.firstListMs` | 942 ms | **26 ms** |
| /app.mjs 的 br 响应 | — | 4.8 ms / 22.8 KB |
| 首页的 br 响应 | — | 1.7 ms / 6.5 KB |

代价是多传 11 KB（+10%），换来 55 倍的响应速度——本机与局域网场景这个账很清楚。

顺带排除的怀疑：那七个随页面一起打的接口，服务端实测 0.7–2.3 ms，浏览器里看到的 29–49 ms
是主线程在渲染/排队，不是服务端慢；/api/drill、/api/daily 等没有可优化的热点。

### 证据

- 改动：src/web/compress.mjs（质量按实测固定为 q6 + 压缩结果缓存 + 命中计数）
- 新增测试：test/compress.test.mjs「压缩不再用 brotli 默认的 q11：同一份正文只压一次」
  —— 断言质量 ≤9、第二次请求命中缓存、并给出 500 ms 的时间预算（实测 ~20 ms，修前 1130 ms）
  —— 负向验证过：把质量改回 11 立刻变红，报出「brotli 质量不能是默认的 11…：11」

## 5.115 离线那一半真的能用：断网重开、本机判定、队列自己同步（第 112 轮 / 共 250 轮）

这轮把「离线」当成一个真环境来验：**把服务端整个停掉**，看页面还能不能练。

### 断网实测（服务端进程已被 kill，curl 返回 000）

| 环节 | 实测结果 |
| --- | --- |
| 重开页面 | 外壳由 Service Worker 缓存给出，页面正常起来（缓存名 dsh-learn-shell-0.77.0，10 个资源） |
| 题库 | 来自 localStorage 缓存（361 KB），徽标「离线 · 本地判定」，页头写明「离线：题库来自 2026-09-27 03:25:56 的缓存」 |
| 题表 | 共 568 题、渲染前 60 条，选题与输入框都能用 |
| 判定 | 本机 judge.mjs 判定：「判定：通过（100 分）… 已命中 1 / 1」，实时区域同步播报 |
| 排队 | 记录进 dsh-learn-offline-queue，徽标变「待同步 1 条」，面板列出时间/题目/判定/分数 |
| 重开一次（仍离线） | 队列仍在（1 条），面板照常显示——离线攒下的东西不会因为刷新丢掉 |
| 恢复后同步 | 记录以**原提交时间**落到服务端（/api/history 可见 03:26:15、client web-ju6fb7、darwin） |

### 发现的问题：说好的「自动」其实要手点

界面上写着「恢复网络后自动并入进度」，实测：服务端恢复后**页面零操作 22 秒，徽标一直挂着「待同步 1 条」**。
原因不是 bug 而是覆盖面不够——`online` 事件只在**系统网络状态**变化时触发，而这次变的是「服务端重启了」：系统网络一直是通的，浏览器没有任何事件可发。

### 改法

队列非空时挂一个 12 秒的定时器自己去试：刚排队时挂上、重开页面发现队列非空时挂上、同步失败仍离线时继续挂；
同步成功（在线且队列空）自动停表，不留下一直打接口的定时器。原来那两条路（`online` 事件、手动「立即同步」）保留不动。

### 实测（改前 → 改后，同一套操作）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 服务端恢复后页面零操作 | 22 秒仍是「离线 · 本地判定（待同步 1 条）」 | **16 秒内**「在线」、队列 0、历史出现该记录 |

### 证据

- 改动：web/app.mjs（`syncOfflineQueueSoon()` / `stopOfflineRetry()`，三个挂载点）
- 新增测试：test/page.test.mjs「离线队列会自己重试（不依赖用户点按钮，也不依赖 online 事件）」

一道题如果整道题只判工具名，学员敲四个字母就满分——它会拉高通过率，让学习计划与建议失真。
所以这轮写了个体检脚本，拿「偷懒答案」把全部题目过一遍。

### 指标（两档，避免把正常题算成问题）

- **漏洞**：要素 ≥2，但只写工具名就 100 分 → 说明某个要素等于没判，必须修；
- **偏软**：只写工具名就 100 分（单要素题本来就可能是「知道用哪个命令」）→ 记在基线里，只许减不许增。

### 实测（576 道题，按平台分别扫）

| 指标 | darwin | linux / win32 |
| --- | --- | --- |
| 漏洞（要素≥2 被工具名骗过） | **0 道** | **0 道** |
| 偏软（工具名即满分） | 2 道（基线） | 同上 |

顺手修掉的一道真放水题：

    netops.arp-scan-subnet   改前要素：arp-scan|arping|nmap -sn|for … in
                             写 arp-scan 就 100 分（题目要的是「扫 10.0.0.0/24」，扫没扫网段根本不判）
                             改后要素：再加一条「扫描范围」
                             实测：arp-scan → 50 分未通过；arp-scan --localnet → 100；nmap -sn 10.0.0.0/24 → 100（正确写法一个都没误伤）

剩下两道偏软题**故意不修**，理由写在基线旁边：`system.memory-snapshot`（macOS 看内存就是 `vm_stat`）、
`netops.time-sync-check`（`timedatectl` 不带子命令也会打印同步状态）——它们的正确答案本身就是裸命令，
硬加第二个要素会把正确写法判成 50 分。**假阴性比偏软更伤学员**，所以这两道留在明处而不是偷偷加规则。

## 5.123 「越熟练越该练」：训练权重的一个反直觉排序（第 120 轮 / 共 250 轮）

这轮审的是学习闭环里最像「智能」的那部分：**今日建议用的是不是对的题**。

### 量出来的排序病

`progress.mjs` 的公式是 `weight = (100 − 最高分) + 练过的次数 × 5`，注释写着「反复没过比一次没过更该先练」。
把三种情况放进「全量」模式实测：

| 题目状态 | 旧权重 | 旧排序 |
| --- | --- | --- |
| 满分、练过 20 次 | **100** | **第 1 位** |
| 50 分、练过 2 次 | 60 | 第 2 位 |
| 从没练过 | 0 | 第 3 位 |

也就是说：**练得最熟的那道题被排在最该练的位置**，而界面上的文案是「按薄弱程度加权」。
根因是次数的加成不看分数——满分题的 `(100 − 100)` 是 0，但 `20 × 5` 把权重顶到了 100。

### 改法

次数加成只在**还没满分**时给（「反复没过更该练」的初衷保留），满分的题权重回到 0；
同时在权重相同时加一条排序规则：**练得少的排前面**——否则满分题（0）会和没练过的题（0）打成平手，
而「全量」模式会把练熟的题排在生题前面。

界面上的公式说明也同步改了（网页版今日建议那一行原本写着旧公式）。

### 实测（真实命令行，先造数据再看排序）

    $ for i in $(seq 1 20); do node src/cli.mjs check linux.platform-probe \"uname -s\" --client=cli-darwin; done   # 满分 20 次
    $ node src/cli.mjs check docker.run-web \"docker run nginx\" --client=cli-darwin                                     # 40 分没过，2 次

| 场景 | 旧 | 新 |
| --- | --- | --- |
| 全量模式第 1 位 | 满分练 20 次的那题（权重 100） | **40 分没过 2 次的那题（权重 70）** |
| 满分练 20 次的题在 linux 轨道里的位置 | 第 1 位 | **第 21 / 21 位**（权重 0） |
| 单元级 | `practiceWeight(100, 9) === 45` | `practiceWeight(100, 9) === 0` |

## 5.124 复习节奏：错过多少次都回同一天，以及「还有 1 天」其实是 1 小时（第 121 轮 / 共 250 轮）

上一轮修训练权重，这轮顺着学习闭环往下看**间隔重复**（复习队列）。把各种历史跑成一个矩阵实测：

| 历史 | 间隔（旧） | 间隔（新） |
| --- | --- | --- |
| 未通过（昨天） | 1 天 | 1 天 |
| 错过 **1** 次后通过 | 3 天 | 3 天 |
| 错过 **3** 次后通过 | 3 天 | **2 天** |
| 错过 **6** 次后通过 | 3 天 | **2 天** |
| 一次通过 | 7 天 | 7 天 |
| 连续通过 2 / 5 次 | 14 / 30（封顶） | 14 / 30（封顶） |

### 两个毛病

1. **错过几次完全不影响复现节奏**：一道反复栽跟头的题和一道偶尔手滑的题，通过之后都安排 3 天后再来。
   这与间隔重复的目的（记不牢的题回得更勤）相反——而这条规则的注释里写的就是「反复没过比一次没过更该先练」，
   只是那句话当时只用在**训练权重**上，没有传导到复习排期。
2. **倒计时把 1 小时说成 1 天**：`waitDays = ceil(剩余/天)`，于是距到期还剩 1 小时时界面写「还有 1 天」。
   复习队列里这条文案就是学员决定「现在练还是明天练」的依据，说错就是误导。

### 改法

- `reviewSchedule` 统计历史未通过次数：`failures >= 3` → 2 天，`failures >= 1` → 3 天（只在连续通过 1 次时生效，
  连续通过 2 次以上仍按 7n 走，不受失败次数影响）；
- 倒计时按**毫秒**判单位：剩余 ≥ 24 小时说「还有 N 天」，不到一天说「还有 N 小时」——正好 24 小时仍然说 1 天，
  避免把边界过度修正。

### 实测

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 错过 3 次后通过 | 间隔 3 天 | **间隔 2 天** |
| 错过 6 次后通过 | 间隔 3 天 | **间隔 2 天** |
| 连续通过 3 次（中间错过过） | 21 天 | 21 天（不变） |
| 距到期还有 1 小时 | 「还有 1 天」 | **「还有 1 小时」** |
| 正好还有 24 小时 | 「还有 1 天」 | 「还有 1 天」（不变） |
| 复习队列里 23 小时后到期的那条 | 「还有 1 天」 | **「还有 23 小时」** |

## 5.126 问「怎么用」，得到一个监听中的进程（第 123 轮 / 共 250 轮）

这轮做远程 agent 的真环境验证（跨机只读执行这条链），顺手在入口脚本上撞到一个很硌人的问题。

### 真环境验证：远程 agent 这条链是通的

    $ node src/agent.mjs --port 8793 --token testtoken123        # 另一台机器上的 agent
    $ node src/cli.mjs verify linux.platform-probe --runner=remote \\
        --endpoint=http://127.0.0.1:8793 --token=testtoken123 --run
    执行后端：remote（http://127.0.0.1:8793）
    验证命令：uname -s
    结果：通过
    说明：远程输出符合预期：Darwin|Linux

安全边界逐条实测：`/agent/exec` 不带 token / token 错 → **401**；命令不在只读白名单 → **403**；
请求体 40 KB（上限 16 KB）→ **413**；`/agent/health` 如实报告 `requiresToken`；
token 只在请求体里读（不是 HTTP 头），默认 `run` 为假时只返回 dry-run 说明。

### 撞到的问题：--help 会起服务

    $ node src/agent.mjs --help
    dsh-learn agent 已启动：http://127.0.0.1:8790      ← 问用法，它开始监听端口了
                                                        （端口被占时抛 EADDRINUSE）
    $ node src/web/server.mjs --help
    dsh-learn Web 客户端已启动：http://127.0.0.1:8787    ← 一样

CLI 的 `--help` 一直是好的，两个服务型入口没有：它们把 `--help` 当成普通参数忽略，照常启动。
端口被占时用户看到的是 `EADDRINUSE`，很容易误判成自己端口配错了。

### 改法

两个入口在 `isMain()` 里先认 `--help`/`-h`：打印用法（含接口、约束、相关环境变量）后以 0 退出。
网页版那处特意用 `isMain()` 判定——被当库 `import` 时即使命令行里带 `--help` 也不该打印用法。

### 实测

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| `node src/agent.mjs --help` | 起服务并一直挂着 | 打印用法，退出码 **0** |
| `node src/web/server.mjs --help` | 起服务 + 启动横幅 | 打印用法，退出码 **0** |
| `import('./src/web/server.mjs')` 且 argv 里有 `--help` | — | 不打印用法、不起服务（导出仍在） |
| 正常启动 | 可用 | 可用（HTTP 200） |

### 证据

## 5.140 平台缺口清零：补 15 个 Windows 变体 + 给「本来就不适用」的题一个说法（第 137 轮 / 共 250 轮）

### 这轮要解决的问题

上一轮把 win32 纳入体检口径后，缺口数是 20，全是「题本身有 darwin+linux 变体，Windows 侧没写参考答案」。
但真正的目标不是把 20 变成 0，而是让这个数字**只代表真的欠着的活**。因为清单里混着两种完全不同的东西：

- **还没写**：查端口占用、看路由表、无线链路这些事在 Windows 上照样要做，只是没人写参考答案；
- **本来就不适用**：`launchctl` 是 macOS 独有的，`pkgutil`/`dpkg` 这种「哪个包装了这个文件」Windows 上根本没有对应概念。

两种混在一个数字里，这个数字就永远清不到零——清不到零的指标没人看，等于又回到「审计看不见 Windows」。

### 改了什么

**1. 题目可以声明自己在哪些平台上成立（`platforms`）**

`src/core/schema.mjs` 校验它（必须是非空数组、且每个名字都在已知平台里——写错成 `macos` 会让这道题在真平台上悄悄逃过体检，
所以必须在入库时就拦住）；`src/core/catalog-audit.mjs` 的 `platformsOf()` 以声明为准，
被声明排除的平台**不参与体检、也不算缺口**。

同时加了一条**防自相矛盾**的规则，而且它当场就抓到了一次真错：我给 `service.launchctl-list` 声明了
`platforms: ['darwin']`，但题目里其实有一个 linux 变体（作为「Linux 上没有 launchctl」的对照）——
体检立刻报错 `platforms 没写 linux，却给了 linux 变体`。改成 `['darwin','linux']` 才对。
规则要求「声明了不适用，就不该又给那个平台的变体」，两条信息必须一致。

最终声明了 `platforms` 的 5 道题：`service.launchctl-list`、`ops.file-owner-package`、
`shell.lowercase-var`、`shell.assoc-array`、`shell.read-lines`（后三道是 bash 3.2 与 4 的写法差异，Windows 上没有 bash）。

## 5.141 不在适用平台上就别判分：把 platforms 声明落实到判定与界面（第 138 轮 / 共 250 轮）

### 这轮要解决的问题

上一轮给 5 道题声明了 `platforms`（launchctl、pkgutil/dpkg、bash 版本差异），审计不再把它们算成平台缺口。
但只做到这一步是"纸面干净"：**学员在 Windows 上仍然能练到这道题，而且能拿到满分**——
因为 win32 没有变体，判定会退回顶层兜底规则，而这道题的兜底规则是 `launchctl|systemctl`。
于是在 Windows 上敲 `launchctl list`，判定器给 100 分，提示"关键要素齐全"。

这条命令在 Windows 上根本不存在。这不是"体验问题"，是**教错**：
学员照这个答案去敲，得到的只会是 `'launchctl' 不是内部或外部命令`。

### 改了什么

**1. 判定层多一道"该不该判"的闸（`src/core/judge.mjs`）**

新增 `platformBlocker(resolved)`：题目声明了 `platforms` 且当前平台不在其中时返回一句人话，
否则返回 `null`。判定内核本身不动（它仍是纯函数，测试与离线判定照旧），
把"能不能判"交给调用方决定——**一处判断，三个客户端共用同一句话**。

**2. 三个入口都拦住，而且都不记录**

- **CLI**：`dsh-learn check` 直接 `exit 2`，把原因写到 stderr，**不写进度**（不能因为平台不适用就给用户留一条"未通过"）；
- **Web API**：`POST /api/check` 返回 **400** + `platformUnsupported: true` + `error` 里的人话，**不记录**；
- **网页版**：提交前先自查（离线判定那条路也拦），并且**服务端拒绝时不再退化成"本地兜底判一份"**——
  原来的 catch 会对任何错误跑一次本地判定，那正好是要避免的错答案；
- **原生端**：提交前查 `task.supported`，把原因写进错误栏、清掉上一次结果、不调引擎。

**3. 顺手修掉一个真 bug：4xx 会把整个界面切成离线态**

网页版的 `api()` 原来是 `if (!res.ok) { markOffline(); throw ... }`——任何业务拒绝（400/404）
都会被当成"断网"，界面顶部挂着"离线，等联网"，离线队列也跟着变。现在只有网络失败与 5xx 才算离线，

题目声明与当前平台不符时，题头显示：

## 5.143 离线体验：把「断网还能练」真的走一遍（第 140 轮 / 共 250 轮）

### 这轮做了什么

离线能力（PWA + Service Worker + 缓存题库 + 本地判定 + 待同步队列）是很多轮之前做的，
但**从来没有真的断网跑过一遍**：仓库里只有静态断言（"代码里有这段逻辑"），
而这轮第一次把服务端真的停掉、在真浏览器里把整条链路走完，立刻抓到两个真问题。

### 真环境实测：断网 → 本地判定 → 恢复网络自动同步

1. 起服务端（`DSH_LEARN_HOME` 指向临时目录，不碰真实进度），页面加载后 SW 装好：
   缓存桶 `dsh-learn-shell-0.105.0`，11 个资源（`/`、`index.html`、`app.mjs`、`judge.mjs`、`platform.mjs`、`progress.mjs`、`knowledge.mjs`、图标、manifest）。
2. **停掉服务端**，重新打开页面：页面照常渲染（60 道题在列表里）、徽标显示 `离线 · 本地判定`——
   外壳来自 SW 缓存，题库与判定规则来自 localStorage 里的 bootstrap 缓存。
3. 点"参考答案"再提交：**本地判定给出 100 分**（用的是 SW 缓存下来的同一份 `judge.mjs`），
   徽标变成 `离线 · 本地判定（待同步 1 条）`，记录进离线队列。
4. **重启服务端**：不用点任何按钮，12 秒内的自动重试把队列冲掉——队列 0 条、徽标回到 `在线`，
   服务端 store 里出现这条记录（`system.cpu-count / 100 / darwin`，答案是当时敲的那条）。

### 抓到的两个真问题

**1. 离线时切平台会"假装切了"。** 请求 `/api/bootstrap?platform=win32` 失败后，
原来的代码直接拿缓存里那一份（darwin 的）当结果用：下拉框显示 Windows，
题目与判定规则却全是 macOS 的——用户会以为"切了平台没生效"，更糟的是用错平台的规则本地判分。
现在会**如实说清楚并把下拉拨回缓存里的平台**：

```
（离线：缓存里只有 darwin 平台的题库，已切回；要练 win32 需先连上服务端）
```

**2. 恢复网络后提示不撤。** `envline` 上那句「（离线：题库来自 … 的缓存）」在联网成功后还挂着——
原来成功分支只清了后来加的 mismatch 标记，`bootstrapCacheAt` 没清。现在两处在成功分支一起归零。

实测（真浏览器，截图 `docs/evidence/web-offline-platform-switch-0.106.0.png` 与
`docs/evidence/web-offline-recovered-0.106.0.png`）：断网时切到 linux → 下拉弹回 darwin 并给出上面那句提示；
恢复网络后再切 linux → 下拉停在 linux、提示消失、工具链行变成 GNU。

### 顺带补的护栏：离线外壳清单必须逐条可取

SW 的 `install` 是"逐个下载、任何一个失败就跳过它"（这是有意的：单个 404 不该让整块离线能力失效），
代价是**清单里有一个资源 404 时不会报任何错**，表现只是"离线打开少一块"。
所以这轮把清单当契约来验，两处都加：

- `test/server.test.mjs`：从服务端真的取 `sw.js`，断言 `__VERSION__` 已替换、缓存名带当前版本、
  `SHELL` 里每个路径都 200，并且清单里必须有 `/core/judge.mjs`（离线判定就靠它）；
- `scripts/verify.sh`：同样的三条（缓存名带版本、`__VERSION__` 已替换、清单逐条 curl），
  检查数 **73 → 76**。

### 性能：一条断言"是不是产品问题"的排查

全量跑测试时 `compress.test.mjs` 偶发红：`br 压缩后的 bootstrap 应在 500 ms 内返回，实际 1251 ms`。
没有直接调阈值，而是先量：单独跑服务端连打 6 次 `/api/bootstrap`（带 `accept-encoding: br`）——
**冷压缩 136 ms（550 KB → 缓 存），之后 5 次全命中缓存、23–37 ms**，
`compressionStats()` 也确认命中数在涨。也就是说 1251 ms 那次**全是缓存命中**，
慢的原因是 `node --test` 并行跑几十个文件时同进程被调度噪声打爆，不是产品回归。

修法是把这条时间断言改成**取 5 次里的最小值**（要盯的是"一次同步压缩不会卡住事件循环"，
不是"在最忙的一刻也能 20 ms 返回"），并把这组实测数字写进注释。改完连跑三次全绿。

## 5.144 真仓库实测：一个 Go 项目被识别成「缺 YOLO 知识点」——知识点匹配的精度修复（第 141 轮 / 共 250 轮）

### 这轮做了两件事

1. **Windows 轨补 5 道「写操作先预演」的题**（`-WhatIf`）：停服务、递归删目录、改注册表、放行端口、建共享——
   全部是"先看它要做什么，再去掉 -WhatIf"的安全变更习惯；难易标注与口径一致（其中放行端口 6 要素 = 困难）。
   windows 轨 10 → **15 道**，题库 597 → **602 道**，知识点 155 → **156**。
2. **用真 GitHub 仓库把「克隆 → 解析知识点 → 出草案」整条链路跑了一遍**，当场抓到一个精度 bug（见下）。

### 真环境：`learn-repo gin-gonic/gin`

```
注意：本机 git 配置把 https://github.com/gin-gonic/gin 改写成了 https://ghproxy.net/...（因 insteadOf），
      所以这一趟走的不是直连。
已克隆：~/.dsh-learn/projects/gh-gin/repo/gin-807303（130 个文件）
技术信号：ci（3 个工作流）、go（go.mod 等）、make（Makefile）
草案包：repo-gin　4 道题（识别 4 条命令示例）　涉及轨道：go、network　需要人工复核：3 道
```

链路本身是通的，也如实报告了"走的是镜像而不是直连"。**但知识点识别结果是错的**：
它说这个 Go 项目"识别出 30 个知识点，覆盖 17 个模块"，其中包含 **目标检测 / YOLO（3）** 与 **Python 工程（3）**，
并推荐了 YOLO 训练、mypy 类型检查这类完全不相干的题。

### 根因：词条按子串匹配，短记号与英文单词同形

`src/core/knowledge.mjs` 的 `matcher()` 对普通词条一律做**大小写不敏感的子串匹配**。于是：

| 词条 | 在 Go 项目文本里实际命中的东西 |
| --- | --- |
| `sed` | u**sed**、ba**sed**、clo**sed** |
| `tar` | s**tar**t |
| `df` / `du` | 文件路径、`du` 出现在别的词里 |
| `conf` | **conf**ig、**conf**igure |
| `iou` | var**iou**s、prev**iou**s、ser**iou**s |
| `mAP` | `map[string]string` |
| `engine` | `gin.Engine` |
| `profile` | Go 的 pprof |
| `requests` | 英文里"请求"的复数 |
| `previous` | 想表达 `kubectl logs --previous`，但英文正文里到处都是 previous |

一个 Go 仓库因此"缺 YOLO 与 Python 知识点"——**推荐方向都错了**，而这条链路正是用户要的
「克隆一个项目 → 解析知识点 → 生成题目」。

### 修法（一处判断 + 几条词条）

**判定层**：短 ASCII 记号（≤5 个字母数字）改成**整词匹配**（前后不能紧邻字母数字），长词条保持子串匹配。


```js
const strong = hits.filter(function (hit) { return !HOMOGRAPH.has(String(hit.word).toLowerCase()); });

```

所以给 `repoDigest` 加了 `includeFileList`（默认仍然带上，notes 里要展示"扫了哪些文件"），
**只在进行知识点匹配时关掉它**。

## 5.146 草案要素：URL、路径与设备文件也算"目标对象"（第 143 轮 / 共 250 轮）

### 这轮要解决的问题

前两轮把「真仓库 → 知识点」这条链路的精度修好了，剩下一半是**「→ 生成题目」**：
`learn-repo` / `learn-site` 会把命令示例变成草案包，但真仓库实测（gin）出来的 4 道草案里有 **3 道被标成
「要素太少（只有工具名），可能是废话题」**——这样的草案推广成正式题，就是"敲个工具名就满分"的软题。

### 根因：`isBareWord()` 把 URL 和路径排除在目标之外

草案的要素来自 `ruleHints()`：子命令（第二个词）+ 目标对象（结尾的裸词）+ 最多 3 个选项。
而 `isBareWord()` 明确排除斜杠（当初是为了不把路径当目标），于是**文档里最常见的接口示例一条都抽不到目标**：

```
curl "localhost:8085/bookable?check_in=2030-04-16&check_out=2030-04-17"
→ 要素只有 curl 一个
```

顺带还发现第二个问题：**短开关会把后面的 URL 当成自己的值吞掉**——
`curl -v localhost:8088/thinkerou/987fbc97` 得到的要素是 `-v localhost:8088/thinkerou/987fbc97`（一个要素），
选项与目标粘在一起，等于只判了一件事。

### 改法（三处，都在 `site-learn.mjs`）

1. **新增 `targetOf()`**：裸词之外，**带引号的参数、URL、路径、设备文件**都算目标。
   URL 会先去掉查询串（`?a=1&b=2`）——那部分每次都不一样，这道题要考的是"写对主机与路径"；
   带 scheme 的完整 URL（`https://example.com/a/b`）与绝对路径（`/dev/tty.usbserial-1420`）也认。
2. **目标的选择顺序**：先找**路径/URL 形态**的词（`looksLikePath()`），没有再退回"结尾的裸词"。
   于是 `stty -f /dev/tty.usbserial-1420 115200 cs8` 的目标是设备文件，而不是尾巴上的 `cs8`。
3. **开关不吃 URL**：短开关后面跟着的如果是 URL/路径形态的词，就不把它当成自己的值——
   `-v` 仍是 `-v`，URL 仍是目标。

| --- | --- | --- |

| `curl "localhost:8085/bookable?…"` | 1 要素 | 2 要素（**仍被标"要素太少"，这是实话**：这条示例本来就只有工具名与接口，没有选项） |

## 5.147 深色模式实测：整页不可读——把颜色收成主题令牌并加对比度护栏（第 144 轮 / 共 250 轮）

### 这轮做的是无障碍与可读性

先做了一轮自动化体检（在真页面里跑脚本，不是读代码猜）：**155 个可交互元素，0 个没有可访问名**、

### 真正的问题在深色模式

`index.html` 的 `:root` 里写着 `color-scheme: light dark`，**但样式里从来没有给 `body` 设背景**：
系统用深色模式时，浏览器按这个声明把**画布刷成深色**，而页面文字仍是深色（`--muted: #5b6672`、正文近黑）

`background: var(--bg); color: var(--fg)`（这一句就是那个 bug 的根因）。

顺带修掉一处**实测不达标**的颜色：浅色的 `--warn-text`（离线徽标文字）原来是 `#b26a00`，

## 5.149 原生端「每日一题」的理由被重复包了一层括号（第 146 轮 / 共 250 轮）

### 这轮抓到的 bug：一句话被拼了两遍

上一轮的真机截图里，左栏"每日一题"那一行写的是：

```
每日一题                                该复习了（该复习了（已逾期 1 天）
```

服务端给的 `reason` **本身就是完整一句话**（`该复习了（已逾期 1 天）`，见 `reviewSchedule()` 里那句注释：
"到期理由要写逾期了多久"），网页版与命令行都直接用它；只有原生端又套了一层括号：

```swift
case "review": return "该复习了" + (pick.reason.map { "（" + $0 + "）" } ?? "")
```

于是变成"该复习了（该复习了（已逾期 1 天））"。这不是显示不全，是**同一条信息说了两遍**，
读起来像程序出了错，也让人怀疑"是不是我逾期了两次"。

### 改法

`dailyReason` 里对 `review` 这一支**直接照抄服务端的句子**（空值才回退到"该复习了"）；
`weak` 那一支保持客户端自己组合（服务端给的是"最高 60 分，练过 2 次"这种统计口径，
这里要的是"上次没满分（最好 60 分）"的说法，两者不冲突）。

顺手把同类写法全查了一遍：其余带括号的拼接都是数字/标签（`已导出到 X（12 KB）`、
`难度（169）`、`之后到期：a（2026-09-28）`），没有第二处把服务端的整句话再包一层。

### 新增护栏（原生自检）

`app/macos/selftest.swift` 里加了两条断言（自检总数 97 → **99**）：

- `pool == "review"` 时 `dailyReason` 必须**原样等于**服务端那句 `该复习了（已逾期 1 天）`；
- `pool == "weak"` 时仍是客户端组合出的 `上次没满分（最好 60 分）`。

护栏放在原生自检里，因为这是 SwiftUI 一侧的文案逻辑；`scripts/verify.sh` 每次都会编译并跑它。

### 实测证据

- 原生自检：**99 项全过**（含新增两条），`node --test` **357/357**，`bash scripts/verify.sh` **PASS 76 / FAIL 0**。
- 真机截图（980×652 窗口，窗口原图）：`docs/evidence/native-daily-reason-0.112.0.png`——
  现在读作 `每日一题　该复习了（已逾期 1 天）`；修前的同一位置见
  `docs/evidence/native-left-column-before-0.111.0.png`（那张上面还能看到重复的括号）。
- 三端口径核对：网页版与 CLI 显示的都是 `来源：该复习了（已逾期 1 天）` 这一句，只有原生端拼错了。

### 顺带记一次"没做成"的尝试

这轮本想给原生端做**真机交互验证**（用 AppleScript 驱动：点文本框 → 输入答案 → ⌘↩ 提交 → 截图看判定面板），
权限是够的（`System Events` 能查到前台进程、`click at {x,y}` 也解析到了"text area"元素），
但**按键没有落进输入框**：窗口不是 key window 时 `keystroke` 不生效，试了 `set frontmost` 与
`open -a` 两种激活方式都没成。截图字节完全一致（说明界面真的没变），所以这不是"看起来没生效"。
结论：原生端的**输入类**交互暂时没法自动驱动，静态截图 + 自检仍然是这条链路的主要证据；
要真做下去得走 XCUITest（需要 Xcode 工程），先记在待办里。

## 5.150 同一句话在三个客户端拼了三遍：把「每日一题的理由」收成服务端一份文案（第 147 轮 / 共 250 轮）

### 上一轮的 bug 牵出这一轮的问题

上一轮修好了原生端把服务端的 `reason` 又包一层括号（`该复习了（该复习了（已逾期 1 天））`）。
顺着查下去发现**这不是一个客户端的笔误，而是"三端各拼一份句子"的结构问题**——

| 客户端 | 原来的写法 | review 时的实际显示 |
| --- | --- | --- |
| 网页版 | `label = pool === 'weak' ? '需要重练' : '还没练过'`，再拼 `reason` | **来源：还没练过　该复习了（已逾期 2 天）**（自相矛盾） |
| 命令行 | `来源：` + `pool === 'weak' ? '需要重练' : '还没练过'` | **来源：还没练过**（该复习的题被说成没练过） |
| 原生端 | review 用服务端的 reason，weak 自己拼"上次没满分（最好 N 分）" | 上一轮的重复包括号 |

三处都不是"显示不全"，是**同一条信息被各写一遍、还写歪了**。

### 改法：服务端给一句，客户端只显示

`src/core/progress.mjs` 新增 `dailyWhy(pool, pick)`，由 `dailyPick()` 带出 `why` 字段：

```
review → 该复习了（已逾期 2 天）     ← 复习计划算出来的那句（含逾期几天）
weak   → 上次没满分（最好 40 分）
new    → 还没练过
```

三个客户端一律**原样显示 `why`**：

- 网页版 `renderDaily()` 删掉自己拼的 label（顺带修掉 review 时那句矛盾的"还没练过"）；
- 命令行 `daily` 的 `来源：` 直接用 `why`；
- 原生端 `dailyReason` 先看 `why`（`DailyPick` 加了字段），没有才回退到本地那几句。

### 实测

- 命令行（真实进度里有一条逾期 1 天的复习题）：`每日一题（2026-09-27，来源：该复习了（已逾期 1 天））`；
  修前这里是 `来源：还没练过`。
- 接口：`GET /api/daily` 返回 `{"pool":"review","why":"该复习了（已逾期 2 天）","reason":"该复习了（已逾期 2 天）"}`。
- 网页版（真服务端 + 真浏览器，浏览器里实际渲染出来的一行）：
  `来源：该复习了（已逾期 2 天）` —— 修前是 `来源：还没练过　该复习了（已逾期 2 天）`。
- 原生端自检：新增/改写三条断言（`why` 原样显示、weak 的原样显示、没有 `why` 时回退），自检 **99 → 100 项全过**。

  `bash scripts/verify.sh`：**PASS 76 / FAIL 0**。
